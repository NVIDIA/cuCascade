## Are these cold runs?

**The saved artifact-regime 1.60065% suite reduction measured warm repetitions, not cold scans. Its normal-consumer value inference is withdrawn as explained above.** The command omitted both `--profile` and `--mode`, used the explicitly configured Sirius input cache with LRU retention, and ran each query four times back-to-back on one connection. Query iteration 0 was excluded; the median of iterations 1–3 contributed to the result. Each independent process starts a new engine and applies file `posix_fadvise(DONTNEED)` once at startup. It does not reset Sirius's input cache or repeat OS-file eviction between measured iterations or query groups. **Both corrected policies retain this same four-iteration grouped protocol.** Disabling raw input caching removes that retention mechanism; it does not make the measured iterations uniformly cold in CUDA/context/metadata/operator/allocator state.

This differs from the canonical `--profile cold`, which resets the Sirius input cache and applies file-fadvise before every query invocation in round-robin order. That profile still retains the CUDA context and compiled/planning/resource state: it is input-cold rather than a fresh process for every query. File-fadvise is an advisory hint; it does not prove physical media access, and the configured Sirius path reads compatible operations with `O_DIRECT` anyway. `--mode grouped` would flush once before each query group; that option was not used.

The warm object here is **undecoded input in pinned host chunks**, plus parsed footer metadata. It is not a pinned decoded GPU table. `--pin none` disables explicit table pinning; it does not disable `scan_manager.cache`. On a cache hit, raw Parquet ranges can be copied from host chunks to the GPU and decoded again. Thus warm input does not imply that decoding, copies, host metadata staging, or cuDF synchronization disappear. Cache pressure and partial-range behavior can still cause some input misses; the protocol alone does not prove every byte of every query is resident.

## Which settings can change the apparent allocator benefit?

These are static mechanisms and hypotheses, not measured alternative prices:

- **Input caching and pinning.** Sirius raw-input LRU removes repeated storage reads when data stays resident, while keeping Parquet decode and host/device staging. Uncached `mode: none`, buffered `mode: os`, idle eviction, explicit GPU/host table pinning, and compressed pinning exercise different paths. GPU table pinning can bypass Parquet decode entirely; host table pinning removes Parquet decode but still requires host/device movement. The fraction of elapsed time available to this particular allocator changes with those paths.
- **Batching and data layout.** The 512 MiB scan/hash/concat targets and 90 MB hash-build threshold change task counts, cuDF call shapes, join modes, and host temporary sizes. Smaller batches can create more repeated staging requests; larger requests can cross costly allocation size classes or the 256 MiB cache cutoff. Row-group layout, codec, projected columns, and the SF50 working set also affect this distribution. The standalone diagnostic already demonstrated strongly size-dependent allocation cost, but does not identify the old suite's size distribution.
- **Concurrency.** Pipeline/creator/scan widths change CPU overlap with GPU work, stream queues, allocator lock pressure, and whether an expensive host allocation delays the critical path. An API-duration sum over overlapping threads is not the end-to-end time recoverable by eliminating that API.
- **Memory budgets and spilling.** GPU/host limits and partition sizes change reservation pressure, spill/upgrade transfers, and waits. Many such allocations use the fixed-size host pool or GPU RMM resource, rather than the small/large cuDF pinned resource changed in this PR. This cache cannot remove every malloc or transfer appearing in a trace.
- **Lifetime and working set.** The PR's large-buffer cache is distinct from the Sirius input cache. Resetting input-cache chunks does not automatically purge this allocator's retained large buffers. Its resource lifetime, size-class working set, and 256 MiB cap determine how much reuse survives across queries. The 24 GB host capacity is not the large-cache limit.
- **Instrumentation.** Quent was explicitly off in both timing arms. Profiling and telemetry can change synchronization/API timings; they belong to attribution runs, not the unprofiled suite price. Both arms otherwise held configuration and dependencies constant.

## Were the earlier sync/copy/malloc observations artifacts?

The old main large-buffer path really calls `cudaHostAlloc`/`cudaFreeHost`; this is confirmed statically and by current traced executions. The cache removes repeated registration/allocation calls while retaining the underlying work. That mechanism is real, not created by a "cold" label. Allocation count, byte sizes, overlap, and resulting end-to-end percentage are configuration-dependent.

Copies and synchronization can remain necessary on the warm raw-Parquet path. A `cudaStreamSynchronize` duration includes time awaiting queued work; it is not automatically avoidable synchronization overhead. GPU-memory allocation, I/O-buffer allocation, host staging, raw-input H2D copies, metadata copies, and spill copies must be identified separately. This PR prices one subset. A profile showing large aggregate sync/copy/malloc time is evidence to investigate that configured path; it does not by itself price another configuration or predict the cache's whole-query gain. Root/reviewer own the current matched Nsight interpretation; this static assessment does not substitute new unmeasured percentages for it.

## Independent corrected-result audit and final recommendation

**Retain the bounded large-allocation cache, enabled by default with a 256 MiB limit on this resource.** The consumer chooses whether to use/register the resource; caching itself is enabled by default. Static allocator value, focused correctness checks, large lifecycle gains, and the corrected consumer suite now all support that decision. The measured consumer benefit is meaningful under both tested input policies, rather than resting on the withdrawn 1.6% result. The small 19 MB standalone Parquet fixture still shows no demonstrated application gain; it made only three small large-class allocations per read and is a different workload.

Independent recomputation from both raw `MANIFEST.json` run sets and their CSVs agrees with `CORRECTED-RESULTS.json`. Each policy contains all 11 prescribed processes: three noise baselines, then four baseline and four candidate processes in `BCCBCBBC` order. Each process has 22 queries × four finite, positive timings. The figure of merit sums each query's median of iterations 1–3, then takes the median of the four process sums per arm. Summing across query medians is this prespecified suite metric; it is not a simultaneous multiquery wall-clock measurement.

All four adjacent pairs improve under each policy; all four candidate process totals are below all four baseline totals within each policy. The effects exceed the observed three-process baseline noise ranges. Those ranges are descriptive variability, not confidence intervals, and four processes per arm do not establish a universal price. Per-query results are exploratory: two query point medians under `none` are slower, so the suite result does not establish that every query improves.

The difference between policies is **2.774 percentage points** of suite time reduction, or 467.276 ms saved with cached input versus 307.214 ms with `none` in their respective suite medians. The only YAML difference is input-cache mode, but that policy also changes automatic input readahead and cache-backed staging/retention. It therefore demonstrates a configuration interaction for this coupled policy. It does not isolate an LRU-only or readahead-only effect, and it does not price different batch sizes, thread counts, pinning, capacities, default parser configuration, or physical-media coldness.

The excluded first iteration of each query provides a supplementary descriptive check: the sum of first-query-iteration times has median reduction **5.356%** with Sirius input caching (8.788375 s → 8.317690 s) and **3.140%** with `none` (9.425470 s → 9.129547 s). These first iterations share one process: previous query groups, CUDA initialization, metadata, device/operator pools, and the PR cache can influence later queries. They are not uniformly cold queries, and their sums are not a fresh-process cold suite measurement. Neither the primary hot result nor this supplementary check resolves a fully cold-storage workload.

The audit also checked all **1,936 CPU-validated iterations** across both policies. Every query has the same row count and digest across all arms, policies, noise processes, and iterations; each process independently reports 88 query starts, completions, and GPU-engine entries with no error. Config copies and runner hashes match the frozen manifests; rendered query hashes are identical within each policy. The policy configs differ only in the `mode` line. GPU execution, builds, and loader probing were performed by root/developer/reviewer, not this architect.

Build equivalence is now materially stronger: the corrected direct-object builds retain the 333 unchanged core objects plus the necessarily rebuilt allocator-owning object, the unchanged cuCascade dependency members, and the exact baseline/candidate allocator substitutions. Independent review checked duplicate object-member handling, link arguments, member bytes, dynamic symbol bindings, and loader registry address equality. This establishes the relevant shared RMM resource behavior. The scope remains a frozen, source-equivalent consumer build with the documented dependency revisions; it is not a fresh full build of every current shared-library default. Functional checks and matching registry behavior justify the corrected consumer inference within that scope.

The remaining attribution boundary is separate from the suite price. Corrected hot Q18 profiling is being collected by root.
