# GDS / cuFile for analytics-style disk-to-GPU reads: field evidence and tuning guidance

> **Status.** Research dossier compiled 2026-10-14 from public sources (NVIDIA documentation, papers, white papers, forum threads, GitHub source and issues). Nothing here was verified on GDS hardware, and no published GDS measurement on GB200/GB300 was found. kvikIO is deliberately confined to section 7 and treated as low-confidence evidence. The conclusions that matter for the reactor are in [gds-reactor-recommendations.md](gds-reactor-recommendations.md); NVIDIA's own documentation is summarised in [gds-cufile-best-practices.md](gds-cufile-best-practices.md).


Prepared for the cuCascade disk reactor: `cuFileHandleRegister` on an O_DIRECT fd, `cuFileReadAsync` into unregistered device buffers, POSIX `pread` fallback for reads below 1 MiB, parquet byte ranges known up front.
Research date: 2026-10-14. Web research only; no repository file was modified.
Revision note: kvikIO was demoted to a short, low-confidence section on project guidance. The weight of the dossier is now NVIDIA's own cuFile documentation, direct cuFile users, and published GDS-versus-host-bounce measurements.

## 1. Top findings (read this first)

1. NVIDIA's own table (Best Practices Guide, section 4) says the async/stream API has "Higher execution latency for IO size (<1 MB)" and "Needs multiple streams to submit in parallel"; the thread-pool sync `cuFileRead` is "Better for medium-sized IO requests of 64K and above" with "Higher CPU cost for smaller IO sizes (4k-64k)"; the batch API targets many small (<64 KB) non-contiguous IOs. [DOC] https://docs.nvidia.com/gpudirect-storage/best-practices-guide/index.html
2. The async/stream API depends on cuFile's internal thread pool (`execution.*` in cufile.json, default `max_io_threads` 4). The troubleshooting guide's entry "cuFile async I/O is failing" names "the internal thread pool is not enabled" as a common cause. [DOC] https://docs.nvidia.com/gpudirect-storage/troubleshooting-guide/index.html (section 5.17)
3. `cuFileStreamRegister` flag `0xF` ("All inputs are aligned and known at submission time") "will perform best". Without it, size, offsets and bytes_read pointers are evaluated at execution time. kvikIO never calls it from `read_async`. A reactor that knows ranges and aligns them can use 0xF. [DOC] https://docs.nvidia.com/gpudirect-storage/api-reference-guide/index.html (section 5.4.1/5.4.3); [SOURCE-CODE] kvikIO `cpp/src/file_handle.cpp` `FileHandle::read_async`.
4. Unregistered destination buffers are served from cuFile's internal GPU bounce buffers (extra staging and a device-side copy); NVIDIA says registration is worth it only for reused buffers and "incurs a significant performance cost" to be amortized. Registered-memory pitfalls: `cuFileBufRegister` failing above ~256 MB on one GPU (error 5016), `nvidia-fs` deadlock if registered memory is freed without deregistering. [DOC] best-practices and API reference, release notes known issues; [MEASURED] forum thread 351408.
5. Request-size evidence from direct cuFile users converges on MiB-scale requests: NVIDIA's original cuDF integration found best throughput at "8-32 threads and 1-16 MiB slice size" (default 16 threads, 4 MiB); DALI's chunk default is 2 MiB (range 4 KiB to 16 MiB); ServerlessLLM (host path) uses 16 MB chunks; NIXL `max_request_size` is 16 MB; the DaMoN'26 Parquet study says column chunks of about 100 KB (the DuckDB default) are too small for GDS, which needs MiB-scale transfers. [MEASURED]/[DOC]/[SOURCE-CODE], details in sections 3 to 6.
6. GDS is not automatically faster than a good host path. Measured: GDS 26.4 GB/s versus pread+cudaMemcpy bounce 25.8 GB/s on four 7 GB/s NVMe (fastsafetensors, A100, PCIe4); gdsio GDS 5.23 GiB/s versus CPU_GPU 9.23 GiB/s on an 8 x RTX A5000 box (NVIDIA staff suspected PCIe distance between GPU and NVMe); "almost identical" throughput at all block sizes except 4 KiB in KIOXIA's gdsio study. GDS wins on CPU load, page-cache footprint, robustness under co-located memory-heavy jobs, and when host memory or PCIe root bandwidth is the bottleneck (NVIDIA DGX tables; DeepNVMe 9.6 versus 7 GB/s). [MEASURED]
7. PCIe topology and NUMA decide the GDS outcome. NVIDIA's DGX-2 gdsio example: 6.52 GiB/s at 1.2 ms when the GPU shares a PCIe switch with the NVMe, 3.89 GiB/s at 2.0 ms when not. fastsafetensors: ignoring NUMA hurt GDS while the non-GDS path improved. [DOC]/[MEASURED]
8. A parquet scan engine built on GDS reached 23.4 GiB/s of a 25.6 GiB/s four-SSD ceiling only after four non-I/O fixes: chunked reads (2.9), metadata caching (8.5), pinned memory (12.6), removal of implicit stream syncs ("mis-sync", 23.4). The scan micro-benchmark (Fig. 9/11) uses 8 threads in total across the four SSDs; the end-to-end TPC-H setup uses 8 CPU threads per SSD (section 6.1). [MEASURED] PystachIO, arXiv 2512.02862 (read directly).
9. On Grace-Hopper the GDS-versus-CPU gap narrows ("NVLink-C2C fabric narrows the GDS/CPU bandwidth gap vs. x86+PCIe") and pinned H2D is far faster (135 GiB/s on GH200 versus 57 GiB/s on H200 PCIe, 500 MiB async copies). A host-bounce path is therefore a first-class option on Grace. [MEASURED] U-Tokyo JHPCN FY2025 report (read directly); Verda blog.
10. Operational hazards documented by NVIDIA and users: "All APIs are thread-safe", but `fork()` is unsupported; CUDA graphs are not supported with the stream APIs; `CUFileThreadPoolWorker` asserts if the GPU compute mode is EXCLUSIVE_PROCESS/PROHIBITED; some cuFile versions close stdin in `cuFileDriverOpen` (DALI guards with dup/dup2); `cuFileDriverClose_v2` is reference counted (old close destroyed the library for other modules); upstream kernels 6.11+ regress small (<=128 KB) GDS IO; the host this session runs on reports Linux 7.0.0 (nvidia-fs supports 7.0 since GDS 1.18). [DOC]/[SOURCE-CODE]
11. cuFile has a programmatic parameter API (`cuFileSetParameterSizeT/Bool/String`, "Should be called before the driver opens") covering io threads, queue depth, max direct IO size, bounce buffers, poll mode, `PREFER_IO_URING`, `FORCE_ODIRECT_MODE`, `STREAM_MEMOPS_BYPASS`, `USE_PCIP2PDMA`. kvikIO exposes almost none of it. The newest release notes also say the max direct IO chunk default is no longer 16 MiB ("To retain the previous 16 MiB maximum direct I/O chunk size, set max_direct_io_size_kb to 16384"). [DOC]
12. Recommendation (see final section): call `cufile.h` directly through a small dlopen wrapper that you own, rather than through kvikIO's `cuFileAPI` shim; keep the shim's useful ideas (lazy load, context push, malloc'd async args) and drop its all-or-nothing symbol loading, process-wide static driver lifecycle and silent compat decisions. [INFERENCE]

## 2. What NVIDIA's cuFile documentation says (authoritative layer)

### 2.1 Data path, buffers, alignment

- [DOC] cuFile is "a suitable match for coarse-grained streaming transfers", not fine-grained random access (Overview Guide 1.1.3). "The latency improvements from GDS are most apparent with small transfers." "On some systems, a direct path ... offers at least twice the peak bandwidth as compared to taking a data path through the CPU." (1.2.1). Compat-mode performance "is generally at least the same or better than current CPU-based APIs" (1.2.3). https://docs.nvidia.com/gpudirect-storage/overview-guide/index.html
- [DOC] Since CUDA 12.2 / GDS 1.7: non-O_DIRECT file descriptors are accepted, and for page-aligned buffers/sizes/offsets cuFile still takes the O_DIRECT path (Overview 1.2.1; API reference 5.2.1). tmpfs does not support O_DIRECT (release notes, Known Limitations). https://docs.nvidia.com/gpudirect-storage/release-notes/
- [DOC] cuFile accepts device memory (`cudaMalloc`, `cudaMallocManaged`, `cuMem*`) and host memory (`cudaMallocHost`, `malloc`, `mmap`) from 12.2 (API reference section 3/3.2). Stream-ordered allocations (`cudaMallocAsync`, which RMM's async resource uses) are not mentioned either way; I found no guidance. Treat as untested. [INFERENCE] https://docs.nvidia.com/gpudirect-storage/api-reference-guide/index.html
- [DOC] Alignment: an IO is unaligned if `file_offset`, size, `devPtr` or `devPtr_offset` is not 4 KiB aligned; "Unaligned IOs might not be optimal and should be avoided by reading the size value that is specified in multiples of 4KB and the file_offsets value that is specified in multiples of 4KB." Unaligned IO uses internal bounce buffers (Best Practices 4.3.4). https://docs.nvidia.com/gpudirect-storage/best-practices-guide/index.html
- [DOC] Buffers: "The cuFileBufRegister API is optional. If this is not used, instead of pinning the user's memory, cuFile-managed and internally pinned buffers are used" (API ref 4.5). "If the cuFileBufRegister has not been previously called on the buffer pointer, cuFileRead/cuFileWrite will use internal registered buffers" and "Not using cuFileBufRegister might not be performant for small IO sizes" (4.3). "The cuFileBufRegister API incurs a significant performance cost, so registration costs should be amortized" (4.5). Best Practices decision table: register reusable intermediate buffers; do not register one-time large fills (BAR exhaustion, registration latency) or unaligned IO.
- [DOC] `cuFileHandleRegister` "is required and performs extra checking that is memoized to provide increased performance on later cuFile operations" (5.2.1). No latency figure is published; cache handles. [INFERENCE]
- [DOC] Driver: `cuFileDriverOpen` is optional (implicit at first use of HandleRegister/Read/Write/BufRegister, section 3.1); `cuFileDriverClose` implicitly unregisters leftover registered buffers (5.1.2).
- [DOC] "All APIs are thread-safe. The fork system call should not be used after the library is initialized." (API ref section 3).

### 2.2 Which API for which IO (NVIDIA's own table)

[DOC] Best Practices Guide section 4 (cells as returned by the fetch tool):

| API | Submission / completion | Intended use | Pros | Cons |
|---|---|---|---|---|
| `cuFileRead`/`cuFileWrite` (no pool) | sync / sync | single-threaded, single large file, buffers >16 MB | simple | does not help multiple buffers |
| same, cuFile thread pool enabled | sync / sync | single-threaded large buffers, or multi-threaded multiple files and buffers | "Lower submission latency. Better for medium-sized IO requests of 64K and above." | "Scalability limited by number of CPU threads used. Higher CPU cost for smaller IO sizes (4k-64k)." |
| `cuFileBatchIOSetUp/Submit/GetStatus` | sync submit / async completion | many non-contiguous offsets/sizes/GPU buffers, "Each IO request is small (< 64KB)" | lower completion latency and CPU cost | higher submission latency; more complex |
| `cuFileStreamRegister`, `cuFileReadAsync/WriteAsync` | async / async | multiple non-contiguous offsets, CUDA-stream semantics | "Simple to use for CUDA developers ... fire and forget. Lower submission latency" | "Higher execution latency for IO size (<1 MB). Needs multiple streams to submit in parallel." |

- [INFERENCE] NVIDIA's three size remarks (async slow below 1 MB, sync good from 64K, batch for below 64 KB) imply a different cut point per API. The reactor's 1 MiB cut for the POSIX fallback is consistent with the async remark, but it is not derived from a measurement.
- [DOC] Batch API: "submitted synchronously, but executed asynchronously with respect to host thread" (4.7); "Operations in each batch might be reordered" (5.5.2); supported mainly for local NVMe/NVMe-oF file systems or those supporting Linux AIO (API reference "Known Limitations of cuFile Batch APIs"). Release notes: batch size limit tied to bounce-buffer size removed (listed under v1.16 and again v1.18); v1.19 "Added cuFile APIs to perform scatter-gather I/O across multiple buffers" (no API documentation found in the API reference I read).
- [MEASURED] NVIDIA forum 347327 (GDS 1.15.0.42, A10, NVMe-oF): a second batch failed with "invalid size" because entries with non-zero buffer offsets (32 KB) not aligned to the 64 KB GPU page were classified as "mixed I/Os". No reply visible. https://forums.developer.nvidia.com/t/cufilebatchio-fails-with-mixed-ios/347327

### 2.3 cuFileReadAsync / stream semantics

- [DOC] API ref 5.4.3 (verbatim as returned): size/offset/buffer-offset pointers: "Unless otherwise set using cuFileStreamRegister API, this value will not be evaluated until execution time." Size: "If the exact size is not known at the time of I/O submission, then you must set it to the maximum possible I/O size for that stream I/O." Result: `*bytes_read_p` holds bytes read, -1 on IO error, or a negative `CUfileOpError`. "Operations that are enqueued with cuFile Stream APIs are FIFO ordered with respect to other work on the stream and must be completed before continuing with the next action in the stream."
- [DOC] 5.4.1 `cuFileStreamRegister` flags: 0x0 all parameters valid only at execution time; 0x8 "All inputs i.e. buffer offset, file offset and size are 4K aligned"; 0xF "All inputs are aligned and known at submission time". "Using the flag 0XF will perform best as the workflow can be optimized during submission time."
- [DOC] Troubleshooting 5.17: "There could be many reasons for which stream based async I/O can fail. This will be logged in cufile.log. One of the common reasons could be that the internal thread pool is not enabled" (resolution: the `execution` section of cufile.json).
- [DOC] Release notes: stream/async APIs complete in v1.7 (CUDA 12.2); Known Issues/Limitations: "CUDA graphs are not supported with cuFile Stream APIs" (one extraction also tagged it v1.15) and "cuFile Stream APIs for GPFS and WekaFS are supported in compatibility mode only".
- [MEASURED] NVIDIA forum 339782 (A100, local Samsung NVMe, GDS 1.11.1.6, CUDA 12.2, 4 KiB gdsio): sync about 72 us versus async about 149 us ("about 70 us of additional overhead"); Nsight Systems showed `cuFileReadAsync` at about 21 us in one view and about 71 us on the host thread track, `cuFileStreamSubmitIo` at about 67 us, and `cuFileSparseGPU`/`cuFileCopyGPU` kernels on the stream. No NVIDIA reply. This is 4 KiB random; it quantifies fixed per-op overhead, not bandwidth. https://forums.developer.nvidia.com/t/understanding-the-latency-of-4k-read-workload-in-gdsio/339782
- [INFERENCE] The per-op fixed cost (about 70 to 150 us) is the reason small and medium async reads lose; with 4 to 16 MiB requests at 6 to 7 GB/s per NVMe (0.6 to 2.5 ms of transfer time) it is noise.

### 2.4 cuFile configuration surface (cufile.json and `cuFileSetParameter*`)

- [DOC] Programmatic parameters: `cuFileSetParameterSizeT/GetParameterSizeT`: "Should be called before the driver opens and the values take effect after the driver is opened." Size params: `EXECUTION_MAX_IO_QUEUE_DEPTH`, `EXECUTION_MAX_IO_THREADS`, `EXECUTION_MIN_IO_THRESHOLD_SIZE_KB`, `EXECUTION_MAX_REQUEST_PARALLELISM`, `PROPERTIES_MAX_DIRECT_IO_SIZE_KB` ("must be 4K-aligned, that is requested by nvidia-fs driver"), `PROPERTIES_MAX_DEVICE_CACHE_SIZE_KB` ("used internally for unaligned IO"), `PROPERTIES_PER_BUFFER_CACHE_SIZE_KB`, `PROPERTIES_MAX_DEVICE_PINNED_MEM_SIZE_KB`, `PROPERTIES_IO_BATCHSIZE`, `POLLTHRESHOLD_SIZE_KB`, `PROPERTIES_BATCH_IO_TIMEOUT_MS`. Bool params: `USE_POLL_MODE`, `ALLOW_COMPAT_MODE`, `FORCE_COMPAT_MODE`, `EXECUTION_PARALLEL_IO`, `ALLOW_SYSTEM_MEMORY`, `USE_PCIP2PDMA`, `PREFER_IO_URING`, `FORCE_ODIRECT_MODE`, `SKIP_TOPOLOGY_DETECTION`, `STREAM_MEMOPS_BYPASS`, `FS_MISC_API_CHECK_AGGRESSIVE`. https://docs.nvidia.com/gpudirect-storage/api-reference-guide/index.html
- [DOC] Default values listed in the troubleshooting guide (section 3.6 and sample output): `execution.max_io_threads` 4, `max_io_queue_depth` 128, `parallel_io` true, `min_io_threshold_size_kb` 8192, `max_request_parallelism` 4; `properties.max_direct_io_size_kb` 16384 (older), `max_device_cache_size_kb` 131072, `per_buffer_cache_size_kb` 1024, `max_device_pinned_mem_size_kb` 33554432, `use_poll_mode` false, `poll_mode_max_size_kb` 4, `allow_compat_mode` true, `posix_pool_slab_size_kb` "4 1024 16384", `posix_pool_slab_count` "128 64 64". A newer `gdscheck.py -p` sample shows `max_device_cache_size_kb` 393216, `per_buffer_cache_size_kb` 16384, `gpu_bounce_buffer_slab_size_kb` "1024 8192 16384 65536", `gpu_bounce_buffer_slab_count` "128 8 4 2" (a sample, not described as default). Defaults drift between releases: read yours with `gdscheck -p`.
- [DOC, secondary] Meaning of the `execution` keys (a blog restating cufile.json comments): `max_io_threads` = max host threads per GPU for I/O; `min_io_threshold_size_kb` = minimum size before an IO is split; `max_request_parallelism` = max parallelism per request; `max_io_queue_depth` = max queued work items; author: defaults usually fine. https://zenn.dev/yasu_oh/articles/fb0654e3a8f425 . I did not find these descriptions in NVIDIA's HTML; the Best Practices Guide does not document the thread pool parameters.
- [DOC] `max_direct_io_size_kb`: "Larger values ... will result in a reduced number of calls to the IO stack and might result in higher throughput"; multiples of 64K, between 1 MB and 16 MB (Best Practices 3.3). Newest release notes (Known Issues): "To retain the previous 16 MiB maximum direct I/O chunk size, set `max_direct_io_size_kb` to `16384` in `cufile.json`." The new default is not stated; do not assume it is larger. https://docs.nvidia.com/gpudirect-storage/release-notes/
- [DOC] NIXL's GDS plugin (NVIDIA/ai-dynamo) recommends: `allow_compat_mode` true; `max_direct_io_size_kb` 16384; `max_device_cache_size_kb` 2097152; `per_buffer_cache_size_kb` 16384; `max_device_pinned_mem_size_kb` 33554432; `posix_pool_slab_size_kb` [4,1024,16384]; `posix_pool_slab_count` [512,512,512]. https://raw.githubusercontent.com/ai-dynamo/nixl/main/src/plugins/cuda_gds/README.md
- [DOC] Release notes history: v1.6.1 "Implemented threadpool in the cuFile library to enable parallelism and improve throughput"; v1.13 "Improved unregistered buffer IO performance for larger IO size using threadpool", NVMe P2PDMA (ext4/XFS); v1.17 DMA-BUF, user-defined topologies; v1.18 nvidia-fs support for Linux 7.0; v1.19 scatter-gather APIs, RAID1/RAID10 (kernel 7.2+), `vanilla_posix_mode`; newest listed v1.19.1 (September 2026).

### 2.5 Known issues, platform requirements, thread-safety (NVIDIA)

- [DOC] Release notes Known Issues (v1.19.x), verbatim as returned: "`nvidia-fs` can deadlock in `nv_p2p_dma_map_pages` and `nv_p2p_mem_info_free_callback` functions when the user frees CUDA memory without calling `cuFileBufDeregister`." "cuFile APIs are not supported with applications that use the `fork()` system call." "The `cuFileRead` and `cuFileWrite` APIs fail when working on `cuMemMap` allocations with multiple GPUs when the IO request is not 4K aligned." "Due to a change in `pin_user_pages_fast`, upstream kernels 6.11 and later ... exhibit a performance regression for small I/O sizes up to 128 KB" (both nvidia-fs and p2pdma paths). "On Linux 6.17 and later with nvidia-fs mode enabled, the NVMe patch has a known issue with drives that support scatter-gather lists (SGLs)." "NVME P2PDMA can fail on x86_64 platforms when KASLR is enabled." "Prior to CUDA 13.1, enabling stats with verbose logging may cause a race condition during shutdown that can trigger a segmentation fault." "When cufile_stats JSON parameter is set to non-zero, cuFile library may crash during program exit if opened/closed through dl interface."
- [DOC] File systems: ext4 "must be mounted with the journaling mode set to data=ordered. This has to be explicitly part of the mount options" (troubleshooting 16.7/17.6); GDS also needs IOMMU and ACS handled ("PCIe Access Control Services (ACS) forces P2P PCIe transactions to go up through the PCIe Root Complex", Best Practices 3.1); NICs, NVMes and GPUs "should be under a PCIe switch when possible"; GPU kernels should run on the primary context ("Launch GPU kernels on the primary context instead of using a separate context", 3.2).
- [MEASURED] A silent compat-mode example (transcribed from the slide): cufile.log "ERROR cufio-fs:152 EXT4 journal options not found in mount table for device, can't verify data=ordered mode journalling" followed by "NOTICE cufio:1538 cuFileHandleRegister GDS not supported or disabled by config, using cuFile posix read/write with compat mode enabled" (GWDG slides, page 9, read directly). [INFERENCE] Because cuFile continues in POSIX mode instead of failing, a benchmark can run entirely in compat mode without any error.
- [MEASURED] NVIDIA forum 295318 (H100, multi-threaded MONAI): `CUFileThreadPoolWorker::run(): Assertion '0' failed`; NVIDIA staff diagnosis: "The cuda device is not available at this time and as a result the cuDevicePrimaryCtxRetain cuda call fails"; cause: GPU compute mode EXCLUSIVE_PROCESS (old driver 535.129.03); fixed by CU_COMPUTEMODE_DEFAULT. https://forums.developer.nvidia.com/t/cufilethreadpoolworker-run-assertion-0-failed/295318
- [MEASURED] NVIDIA forum 351408 (RTX A6000, no nvidia_fs module): `cuFileBufRegister` fails above ~256 MB with error 5016 (`CU_FILE_INVALID_MAPPING_SIZE`); no reply. https://forums.developer.nvidia.com/t/cufilebufregister-fails-above-256-mb-on-rtx-a6000-48-gb-hbm-with-error-5016-how-to-increase-the-maximum-registration-size/351408
- [MEASURED] NVIDIA forum 277650 (2 x A100-PCIE, PCIe Gen5 U.2 NVMe, GDS 1.8.1.2): gdsio `-x 0` (GDS) at 32 threads and 1M reported 172.3 GiB/s, far above the drives; NVIDIA staff: "yes looks like bug with -x 0 test". Validate gdsio results against device counters and `/proc/driver/nvidia-fs/stats`. https://forums.developer.nvidia.com/t/nvidia-gds-output-exceeds-nvme-device-throughput/277650
- [DOC] nvidia-fs gained Linux 7.0 support in v1.18; the SGL-drive issue above applies to nvidia-fs mode on 6.17+; the small-IO regression applies to 6.11+; RAID1/RAID10 support needs kernel 7.2+. [INFERENCE] The development host reports Linux 7.0.0-38-generic; if the reactor runs on such a host, verify the installed GDS version and run `gdscheck -p` before interpreting any GDS number.

### 2.6 NVIDIA's own gdsio numbers

- [DOC] DGX-2, `gdsio -D /nvme23/gds_dir -d 2 -w 8 -s 500M -i 1M -x 0 -I 0 -T 120` (nvme23 = RAID0 of nvme2+nvme3, ext4): "Throughput: 6.524658 GiB/sec, Avg_Latency: 1197.370995 usecs" when GPU 2 shares the PCIe switch. With GPU 12: "Throughput: 3.893747 GiB/sec, Avg_Latency: 2003.091575 usecs" ("40% decrease in throughput and a 2X increase in latency"); explanation: cuFile selects a GPU on the same PCIe switch as the storage for the data buffers (GPU 0) and then moves data to the target GPU. https://docs.nvidia.com/gpudirect-storage/configuration-guide/index.html
- [INFERENCE] Little's law check on the first run: 8 threads x 1 MiB / 1.197 ms = about 6.5 GiB/s. So roughly 8 MiB must be in flight to hold 6.5 GiB/s on that NVMe pair at that software latency. The same arithmetic suggests about 8 to 16 MiB in flight per 6 to 7 GB/s drive; use as a starting value, not a result.
- [DOC] For random 4K loads "a large number of threads generating load are necessary to assess peak performance"; not relevant to MiB-scale scans.
- [DOC] NVIDIA's 2019 GDS blog (DGX-2, V100): system memory path limit 48 to 50 GB/s total versus local NVMe 53.3 GB/s total (Table 1, as extracted), "decreased end-to-end latency by 3.8x on 80 GB of data". [INFERENCE] The point: the bounce path is bounded by host memory and PCIe root bandwidth mainly when many NVMe feed many GPUs. https://developer.nvidia.com/blog/gpudirect-storage/
- [MEASURED] NVIDIA cuDF blog 2022 (DGX-2, two 3.84 TB NVMe RAID0, Parquet/ORC, 48 data profiles per format, 512 MiB to 4 GiB in-memory): "up to 3-4x higher cuDF read throughput, with an average of 30-50% higher throughput across a variety of data profiles"; at 4096 MiB a 10% to 270% range; IO-bound (poorly encoded) files benefit most. Thread/slice sweep: "We discovered that the highest end-to-end read throughput was for 8-32 threads and 1-16 MiB slice size"; "Small slice sizes cause higher overhead due to the large number of read tasks, and large slice sizes lead to poor utilization of the thread pool"; defaults 16 threads and 4 MiB slices. This was cuDF's own thread pool of fixed-size cuFile calls (pre-kvikIO). https://developer.nvidia.com/blog/boosting-data-ingest-throughput-with-gpudirect-storage-and-rapids-cudf

## 3. Direct cuFile users (not through kvikIO)

## 5. The alternative: multi-threaded O_DIRECT pread into pinned host memory, double-buffered cudaMemcpyAsync

### 5.1 What has been achieved and with what parameters

- [MEASURED] ServerlessLLM: O_DIRECT, 16 MB bulk chunks ("a sufficiently large chunk size in bulk reading (16MB)"), multiple I/O threads per tier, pinned chunk pool, task-queue pipeline between tiers; "with 4 CPU cores, ServerlessLLM can achieve maximum bandwidth utilization"; on a 12 GB/s two-drive PCIe4 RAID0 it reaches normalized bandwidth utilization 1.00 against an FIO baseline of "asynchronous 4M direct sequential read with the depth of 32" (Fig. 6b, Fig. 7). (read directly) https://arxiv.org/abs/2401.14351
- [MEASURED] fastsafetensors fallback: `pread` + `cudaMemcpy`, 160 MB pinned bounce buffer per I/O thread, up to 16 threads per rank, buffered I/O (page cache; the authors note direct I/O "is available in Linux" but they did not enable it because of file-system limits such as tmpfs): 25.8 GB/s against a 28 GB/s stress-test maximum for the four drives. (read directly)
- [DOC] cuFile's compat (POSIX) path has a pinned host "POSIX bounce buffer pool": `posix_pool_slab_size_kb` 4, 1024, 16384 with counts 128, 64, 64 (NIXL recommends 512 each). [INFERENCE] 16 MiB is therefore a vendor-chosen staging unit.
- [MEASURED] DeepNVMe tutorial (AIO path, A6000, drive 5.6 GB/s read): auto-tuned `block_size` 1 MiB, `queue_depth` 32, `overlap_events` true, `intra_op_parallelism` 8, giving 3.69 GB/s read; "For best performance, pinned device or host tensors should be used". https://www.deepspeed.ai/tutorials/deepnvme/
- [MEASURED] DeepNVMe scaling on Azure ND-H200-v5: reads 10 GB/s (4 x Gen4) to 27 GB/s (4 x Gen5) to 48 GB/s (8 x Gen5); the paragraph does not say AIO or GDS. https://pytorch.org/blog/deepnvme-affordable-i-o-scaling-for-deep-learning-applications/

### 5.2 io_uring: what the 2026 study says (VLDB'26, Jasny, El-Hindi, Ziegler, Leis, Binnig)

- [MEASURED] Eight PCIe 5.0 Kioxia CM7-R SSDs, AMD host, kernel 6.15: "With sufficiently large requests, a single core saturates the PCIe 5 SSD array, reaching up to 90 GiB/s for reads and 50 GiB/s for writes. This point is reached for writes at 128 KiB and reads at 256 KiB with +Passthru and +IOPoll enabled." "Larger blocks substantially reduce CPU cost per byte". Worker-thread fallback triggers: block size above `max_hw_sectors_kb` (128 KiB with IOMMU), batches above `nr_requests`, blocks above 512 KiB (`max_segments`). https://arxiv.org/abs/2512.04859
- [MEASURED] Same paper, in a 4 KiB-page buffer manager under YCSB (transactions per second, not raw IO throughput): registered (fixed) buffers about +11%, registered files "minimal benefit", SQPoll about +32%, IOPoll about +21%, NVMe passthrough about +20%; passthrough needs no file system and is limited to 512 KiB blocks.
- [INFERENCE] For multi-MiB sequential reads the per-IO syscall cost is already amortized; the choice between a handful of pread threads and io_uring matters less than keeping enough bytes in flight and avoiding the page cache. Registered pinned buffers help the 4 KiB case, which is not the reactor's.

### 5.3 Host-to-device leg

- [MEASURED] Verda GH200 memcpy test: async host-to-device copy of a 500 MiB buffer, 135 GiB/s on GH200 versus 57 GiB/s on H200 (PCIe5). https://verda.com/blog/data-movement-in-the-nvidia-gh200-grace-hopper-superchip
- [MEASURED] GH200 data-movement study: Grace local LPDDR5X up to about 500 GB/s; cross-C2C accesses "never go above 60% of theoretical bandwidth"; no storage or GDS measurements. https://arxiv.org/abs/2408.11556
- [MEASURED, paper statement] fastsafetensors: PCIe Gen4 x16 is "32 GB/s", "the key factor in determining the maximum throughput" when files are DRAM-resident (tmpfs run, Fig. 15a).
- [INFERENCE] Both paths are capped by the GPU's own PCIe link (57 GiB/s measured H2D on an H200 over PCIe5). The bounce path also moves every byte through host DRAM twice (NVMe DMA in, H2D DMA out), which starts to matter at tens of GB/s (NVIDIA's 2019 DGX-2 table puts the system-memory path at 48 to 50 GB/s total) or when several GPUs share one host. On Grace the extra pass runs at LPDDR5X/NVLink-C2C speeds, so it matters much less.

### 5.4 When each wins [INFERENCE from sections 2 to 5]

| Condition | GDS (cuFile) | Host bounce |
|---|---|---|
| GPU and NVMe under one PCIe switch, ACS/IOMMU handled, ext4 data=ordered or XFS | favored for CPU/page-cache relief; parity on bandwidth for one SSD | parity if well pipelined |
| Many NVMe + many GPUs sharing host root complex/DRAM | favored (DGX tables, DeepNVMe) | host memory or PCIe root becomes the cap |
| Wrong PCIe/NUMA placement | loses 40%+ (rows 1, 5, fastsafetensors NUMA run) | favored |
| Requests under about 1 MiB (async) or under 64 KiB (sync) | NVIDIA says worse | favored; also kernel 6.11+ regression below 128 KB |
| Unaligned or non-O_DIRECT-capable file system (tmpfs) | bounce inside cuFile or compat mode | favored |
| Grace (GH200/GB200): NVLink-C2C | gap narrows; no GB200/GB300 data | strong (135 GiB/s H2D) |
| Many tenants on one host (memory-copy jobs) | more robust (fastsafetensors Fig. 15c) | page cache and memory-bandwidth sensitive |

## 6. Parquet request sizes, coalescing and prefetch across engines

- [MEASURED] DuckDB defaults: 122,880 rows per row group, one page per column chunk, "column chunks on the order of 100 KB once compressed and encoded"; "such small I/O units are suboptimal, as MiB-scale transfers tend to be more efficient"; recommendation: million-row row groups, at least 4M rows for one SSD ("GDS starts to saturate SSD despite the large file size"), 10M rows used; page count 100 or more for decode parallelism. DaMoN'26 (read directly) https://arxiv.org/abs/2602.17335
- [SOURCE-CODE] cuDF parquet reader (branch-24.12 `cpp/src/io/parquet/reader_impl_preprocess.cu`, `read_column_chunks_async`; I could not locate the function in main, so main may differ): groups consecutive column chunks into one read only when `next_offset == io_offset + io_size` (no gap tolerance) and the compressed/uncompressed status and source match ("Not coalescing uncompressed with compressed chunks is so that compressed buffers can be freed earlier"); one device buffer per group rounded up to padding multiple, then `device_read_async(io_offset, io_size, ...)` if `is_device_read_preferred(io_size)` else `host_read` + `cudaMemcpyAsync`; futures collected and waited lazily. In cuDF main `file_source::is_device_read_preferred` always returns true (`cpp/src/io/utilities/datasource.cpp`).
- [DOC] Theseus (arXiv 2508.05029 section 3.3.3, read directly): Byte Range Pre-loading "File headers are retrieved first to identify the precise byte ranges required for scan operations. Sufficiently close byte ranges are then merged to reduce the total number of read operations. The byte ranges are retrieved and stored directly in the task's Batch Holder in GPU or Host Memory" (the gap threshold is not published). The Pre-loading Executor inspects the Compute Executor's task queue and "proactively initiates data transfers to ensure input data required by upcoming tasks is readily materialized". Object-store datasource "coalesces multiple reads into single requests". Fixed-size pinned pool because "Large amounts of page-locked memory are slow to allocate".
- [SOURCE-CODE] Velox defaults (`velox/common/io/Options.h`): `kDefaultLoadQuantum` 8 MiB, `kDefaultCoalesceDistance` 512 KiB, `kDefaultCoalesceBytes` 128 MiB, `DEFAULT_AUTO_PRELOAD_SIZE` 72 MB; `kDefaultFilePreloadThreshold` 8 MB and `kDefaultFooterSpeculativeIoSize` 1 MB in `velox/dwio/common/Options.h`.
- [DOC] Arrow `io::CacheOptions` (`cpp/src/arrow/io/caching.h`): `hole_size_limit` ("maximum distance in bytes between two consecutive ranges; beyond this value, ranges are not combined"), `range_size_limit` (maximum combined range), `lazy`, `prefetch_limit` (default 0; "prefetch up to k merged byte ranges ahead of the range that is currently being read"). Default constants live in `caching.cc` and I could not read them.
- [DOC] spark-rapids tuning guide: "Loading data from fewer, large input files will perform better ... Ideally input files should be on the order of a few gigabytes"; contiguous per-column data "can be very small" so reorder columns. https://docs.nvidia.com/cudf-spark/26.04/tuning-guide.html . From `advanced_configs.md`: `spark.rapids.sql.reader.multithreaded.combine.sizeBytes` default 67108864 (64 MiB), `combine.waitTime` 200 ms.
- [MEASURED] In the 2022 cuDF study GDS helped most on files that encode poorly (large, I/O-bound) and little on well-encoded files where decode dominates (section 2.6).
- [INFERENCE] There is no GDS-specific read-ahead depth recommendation in any source I found. The defensible target is bytes in flight at least equal to bandwidth x end-to-end latency (section 2.6 Little's-law check), capped by free GPU memory (PystachIO regulates queue length per scan to avoid GPU OOM; Theseus preloads only for tasks waiting in the compute queue).
- [INFERENCE] Files written with DuckDB defaults have column chunks of about 100 KB (DaMoN'26); other writers differ, so read the actual chunk-size distribution from your footers. If most chunks are below 1 MiB, most reads sit where NVIDIA says the async path is slow. Merging adjacent and near columns, and rewriting with larger row groups where you control the files, moves reads into the 4 to 16 MiB regime that the sources above favor.

## 7. kvikIO (kept short and factual; all kvikIO-derived guidance is [LOW-CONFIDENCE: kvikIO])

Why this section is short: the project guidance is that kvikIO is not a high-quality basis for GDS best practice. The facts below describe what kvikIO does so that you can reproduce only what you need; none of its defaults is endorsed.

### 7.1 Defaults and what the knobs do

[DOC] https://docs.nvidia.com/kvikio/latest/runtime_settings/ and [SOURCE-CODE] `cpp/src/defaults.cpp` `defaults::defaults()`:

| Knob | Default | Effect |
|---|---|---|
| `KVIKIO_COMPAT_MODE` | AUTO (cuDF sets ON unless overridden; cuDF docs: "ON (default in cuDF)") | ON = POSIX through bounce buffers; OFF = cuFile; AUTO = cuFile if `libcufile.so.0` loads, `/run/udev` is a directory and not WSL |
| `KVIKIO_NTHREADS` (or `KVIKIO_NUM_THREADS`) | 1 (cuDF `set_up_kvikio`: 4) | worker threads in the global pool |
| `KVIKIO_TASK_SIZE` | 4 MiB | `pread` splits into tasks of this size |
| `KVIKIO_GDS_THRESHOLD` | 16 KiB (was 1 MiB until PR #596, merged 2025-03-18) | smaller reads bypass the pool and use POSIX in the caller thread |
| `KVIKIO_BOUNCE_BUFFER_SIZE` | 16 MiB | per-thread pinned bounce buffers (POSIX path) |
| `KVIKIO_AUTO_DIRECT_IO_READ` / `_WRITE` | off / on | opportunistic O_DIRECT for aligned middle section in POSIX path |
| `KVIKIO_AUTO_DIRECT_IO_READ_OVERREAD` | off | align offsets down and sizes up, discard extra |
| `KVIKIO_THREAD_POOL_PER_BLOCK_DEVICE` | off | one pool per physical block device (from 26.02) |

### 7.2 Behavior that matters (source)

- [SOURCE-CODE] `cpp/src/file_handle.cpp` `FileHandle::pread`: host pointers or `size < gds_threshold` or compat mode go to POSIX; the small-device case runs in the calling thread (`make_ready_future`). Otherwise `parallel_io` (`cpp/include/kvikio/detail/parallel_operation.hpp`) splits into tasks of `task_size`; the last task performs the final part and waits on the others. A synchronous `cuStreamSynchronize(nullptr)` precedes cuFile calls when `sync_default_stream` is true. Each task calls `cuFileRead(handle, devPtr_base, size, file_offset, devPtr_offset)` with the allocation base and offset.
- [SOURCE-CODE] No buffer registration and no `cuFileStreamRegister` occur in `pread` or `read_async`; `buffer_register` exists (`cpp/src/buffer.cpp`) but is user-called. `read_async` calls `cuFileReadAsync` directly, or, if async is not allowed, falls back to stream-sync plus synchronous read.
- [SOURCE-CODE] POSIX device path (`cpp/src/detail/posix_io.cpp`, read for `posix_device_read_aligned`): pinned page-aligned bounce buffer from a pool, read, async H2D copy, then `StreamSynchronize` on every iteration, i.e. one buffer at a time per task; overlap comes only from running many tasks. A k-way bounce-buffer ring to pipeline this (PR #913 still an open draft; PR #921 closed unmerged on 2026-08-28 with "Will reimplement using the reactor code structure"); the io_uring prototype (#870) was closed unmerged the same day. [LOW-CONFIDENCE: kvikIO]
- [SOURCE-CODE] `cpp/src/detail/transfer_plan.cpp` (`build_transfer_plan`): a request-coalescing planner with `coalesce_max_gap` and `task_size` exists, but it is used by the remote (HTTP) path, not local `FileHandle`.
- [SOURCE-CODE] Block-device pools (`get_thread_pool_per_block_device`, cached by path and device id) exist; PR #880 notes `KVIKIO_NTHREADS` is then per pool, there is "no way to limit the total threads", device-mapper devices report the dm id, and resolution costs about 940 us uncached.

### 7.3 Documented bugs, regressions, thread-safety items in kvikIO

- [DOC] cuDF issue #12780 / PR #12841 and kvikIO #178: "For small reads and writes the overhead of using cuFile and/or KvikIO becomes significant"; ORC writer 5529 ms (KVIKIO) versus 708 ms (OFF) before a size threshold. https://github.com/rapidsai/cudf/issues/12780 , https://github.com/rapidsai/cudf/pull/12841
- [DOC] kvikIO #850 / PR #880: with one global pool, tasks for different drives "cluster on submission in a sequential fashion"; reporter on a DGX A100 (4 x 6.4 GB/s SSD, about 60 `read_parquet` calls per file at row-group level) needed `KVIKIO_NTHREADS=128` for stable full bandwidth (64 gave about 15 GB/s) and reported 25+ GB/s needing 150+ threads; maintainer test (H100, 4 x Micron 7450, compat mode, cold cache, direct I/O) went 6,237 MiB/s to 11,257 MiB/s (4 threads) and 24,384 MiB/s (16 threads) with per-device pools. https://github.com/rapidsai/kvikio/issues/850 , https://github.com/rapidsai/kvikio/pull/880 [MEASURED][LOW-CONFIDENCE: kvikIO]
- [DOC] #917 (merged 2026-02-04): "per-thread, per-context stream" map in the thread pool lacked a mutex, so concurrent operations could race. https://github.com/rapidsai/kvikio/pull/917
- [DOC] #437: cuFile lacks ordering with null-stream work, so kvikIO synchronizes the null stream by default. https://github.com/rapidsai/kvikio/pull/437
- [DOC] #596 (merged 2025-03-18): futures were `std::async(deferred)` and reported ready early; fixed by thread-pool-owned promises; the PR text says the adverse impact on an ORC cold-cache benchmark "can be mitigated by reducing the default GDS threshold parameter from 1 MiB to 16 KiB" and the author "consider[s] this result acceptable" (per-thread-count deltas are in the PR; I did not reproduce them because the extract was ambiguous about sign and baseline). https://github.com/rapidsai/kvikio/pull/596

### 7.4 Where kvikIO differs from NVIDIA's documentation (side with NVIDIA)

1. Threshold. kvikIO routes everything of 16 KiB and above through cuFile (default since 2025-03). NVIDIA: sync thread-pool cuFile is "better for ... 64K and above" with "higher CPU cost for smaller IO sizes (4k-64k)"; async is slow below 1 MB; kernels 6.11+ regress GDS IO up to 128 KB. The earlier 1 MiB default was closer to NVIDIA's guidance. Use NVIDIA's numbers, not 16 KiB. [LOW-CONFIDENCE: kvikIO] versus [DOC]
2. Parallelism layering. kvikIO splits at a 4 MiB `task_size` in user space and calls synchronous `cuFileRead` per task. NVIDIA's cuFile already has an internal pool that splits requests only above `min_io_threshold_size_kb` (default 8192) and issues up to `max_direct_io_size_kb` chunks; 4 MiB calls are below that threshold. NVIDIA's own table recommends the sync API for "a single large file and large buffers (>16MB)" or a thread pool for multiple files. [INFERENCE]
3. Stream registration. kvikIO never registers streams; NVIDIA says flag 0xF "will perform best". [SOURCE-CODE] versus [DOC]
4. Buffer registration. kvikIO leaves registration to the caller and never amortizes it; NVIDIA's guidance is "register reusable intermediate buffers". Same direction as NVIDIA; it is not a conflict, but there is no default benefit.
5. cuFile parameters. kvikIO sets only poll mode, cache size and pinned size via `DriverProperties` setters; it does not touch `max_io_threads`, `max_direct_io_size`, `PREFER_IO_URING`, `FORCE_ODIRECT_MODE`. [SOURCE-CODE] `cpp/src/cufile/driver.cpp`
6. Thread-count lore. kvikIO maintainers say "many threads (8-32)" and "task size around 4-16MiB" for sequential reads (#598); the NVIDIA cuDF blog found the same 8 to 32 threads and 1 to 16 MiB for its own cuFile thread pool. The agreement is consistent with, but does not validate, kvikIO's defaults (1 thread by default; cuDF 4). [LOW-CONFIDENCE: kvikIO] / [MEASURED]

## 9. Thread-safety, crashes and handle-registration reports (collected)

- [DOC] cuFile: "All APIs are thread-safe"; `fork()` unsupported after initialization; no statement either way about concurrent `cuFileReadAsync` calls on one stream beyond FIFO ordering ("FIFO ordered with respect to other work on the stream"). Parallel submission needs separate streams (Best Practices). I found no NVIDIA statement on, and no user report of, crashes specific to multiple threads sharing one stream. Per-stream serialization is documented; sharing a stream across threads is untested territory. [INFERENCE]
- [MEASURED] `CUFileThreadPoolWorker::run(): Assertion '0' failed` with multiple threads when the GPU compute mode is EXCLUSIVE_PROCESS (forum 295318).
- [DOC] Release notes: CUDA graphs unsupported with stream APIs; stats/logging shutdown crash prior to CUDA 13.1; dl-opened cuFile with `cufile_stats` non-zero may crash at exit; `nvidia-fs` deadlock if registered CUDA memory is freed without `cuFileBufDeregister`.
- [SOURCE-CODE] DALI `CUFileDriverScope`: "v2 API performs proper reference counting"; old close "would simply destroy the library, possibly still in use by other modules within the process"; "cuFileDriverOpen in some versions of cuFile library, can close stdin returning 0 file descriptor to the pool, then dali gets it from the OS opening a file and passing to GDS which cannot handle it properly leading to an error" (workaround: `dup(STDIN_FILENO)` before, `dup2` after if fd 0 became invalid). `dali/util/cufile_helper.h`.
- [DOC] cuDF-Java Javadoc: its read/write methods are "NOT thread safe if the path points to the same file on disk" (likely a property of its per-call handle design rather than a cuFile statement; not verified). https://docs.rapids.ai/api/cudf-java/legacy/ai/rapids/cudf/cufile
- [DOC] Handle registration: memoized validation (API ref 5.2.1). NIXL: path-mode registrations of the same path create separate handles (no dedup). DeepSpeed registers/deregisters per operation and still measures 9.6 GB/s on large transfers. No source quantifies `cuFileHandleRegister` latency. [INFERENCE] cache handles per (device, inode) for the file's lifetime.
- [SOURCE-CODE] kvikIO thread-related fixes: #917 race on the per-thread stream cache (merged 2026-02-04, listed in v26.04.00 notes); `StreamFuture` has no internal locking.

## 12. Implications for a reactor that already knows its read ranges up front (parquet footer parsed, byte ranges known)

All bullets are [INFERENCE] unless a tag says otherwise; the evidence is in the sections cited.

1. **Plan before you read; this is the biggest lever.** Sort ranges per file by offset; merge neighbours when the gap is at most G and the merged span at most C; read each merged span as one request. Start G = 512 KiB (Velox default; gap bytes cost under 0.1 ms of drive time at 6 GB/s versus a 70 to 150 us fixed per-op cost for async cuFile) and C = 16 MiB (cuFile's historical max direct IO, NIXL, ServerlessLLM). Theseus merges "sufficiently close" ranges; cuDF merges only exactly contiguous chunks (section 6). Allocate one device buffer per merged span and hand column chunks pointers into it, as cuDF does, instead of per-chunk reads and copies.
2. **Align everything.** Round span starts down and ends up to 4 KiB; make the destination device pointer 4 KiB aligned (allocator sub-allocations are often only 256-byte aligned; verify on your memory resource, then over-allocate and offset, or use an aligned adaptor) because NVIDIA counts a non-aligned `devPtr` as unaligned IO, which takes the bounce path [DOC]; keep batch-API buffer offsets 64 KiB aligned (forum 347327). The over-read is bounded (below 4 KiB per side).
3. **Route by size, then measure the cut.** After coalescing, spans of 1 MiB or more go to cuFile; the remainder goes to the host path (O_DIRECT pread into pinned memory, then H2D), as you already do. NVIDIA's own guidance (async "<1 MB", sync "64K and above", batch "<64 KB") and the kernel 6.11+ regression below 128 KB support a cut in the 256 KiB to 1 MiB band; sweep it with your real span distribution.
4. **Treat the API choice as an experiment, not a given.** Of the direct cuFile users whose source I inspected, none uses `cuFileReadAsync` for bulk reads; they use sync `cuFileRead` from a thread pool or the batch API (section 3). If you keep `cuFileReadAsync`: one stream per outstanding read lane (FIFO per stream), `cuFileStreamRegister(0xF)` since offsets, sizes and (after alignment) destinations are known, size/offset/bytes_read slots with stable addresses until completion, handle `bytes_read < size` and negative results (DALI loops on partial reads), and raise `execution.max_io_threads` through `cuFileSetParameterSizeT` before `cuFileDriverOpen` because async submissions depend on cuFile's internal thread pool (troubleshooting 5.17; default 4 threads). The fixed async overhead (about 70 us over sync at 4 KiB, forum 339782) vanishes at 4 to 16 MiB.
5. **Prefetch depth from bandwidth-delay, bounded by GPU memory.** Target in-flight bytes of roughly 8 to 16 MiB per 6 to 7 GB/s drive (gdsio Little's-law check); sources that reached drive speed used 8 threads in total for four SSDs in PystachIO's scan test (8 per SSD end-to-end), up to 16 threads per rank for four SSDs (fastsafetensors), or 4 cores for 12 GB/s with 16 MB chunks (ServerlessLLM). Cap queue length by free GPU memory (PystachIO's adaptive regulation) and let the reactor preload only for tasks already queued for compute (Theseus pre-loading).
6. **Keep the I/O streams clean.** PystachIO's gain from 12.6 to 23.4 GiB/s came from removing implicit syncs (pageable-memory copies of tiny counters, Thrust) that stall other streams. In the reactor: no pageable host copies, no `cudaStreamSynchronize` or default-stream syncs on lanes that carry reads, pinned control memory; cache parquet metadata once (PystachIO: 2.9 to 8.5 GiB/s). cuFile sync reads have no ordering against other stream work, so order a freshly allocated or cleared destination before the read with an event or stream sync (kvikIO #437 paraphrases NVIDIA here) and test `cudaMallocAsync`-backed destinations explicitly (I found no NVIDIA statement about them).
7. **Registration policy.** Reading straight into unregistered final buffers means cuFile stages through its internal GPU bounce buffers (NVIDIA docs). If measurements show that stage limits you, mimic DALI: a pool of large (for example 16 MiB) registered staging chunks, aligned reads into them, then a stream-ordered device-to-device copy into the destination. Register only long-lived staging memory (NVIDIA: amortize the cost; BAR limits, error 5016 above about 256 MB on one GPU; always deregister before freeing: nvidia-fs deadlock). Do not assume RMM pool memory is registrable.
8. **Handle cache and lifecycle.** Cache one `CUfileHandle_t` per (device, inode) for the lifetime of the file and share it across threads (APIs are thread-safe); open `O_RDONLY|O_DIRECT|O_CLOEXEC`; if O_DIRECT is refused (tmpfs) use the host path. Open the driver once after setting parameters; close it explicitly at reactor shutdown.
9. **Probe the platform and pick the path at startup.** Check that GDS is active and not compat (`cuFileDriverGetProperties`, cufile.log, nvidia-fs stats), GPU/NVMe PCIe locality and NUMA, ACS/IOMMU, ext4 mounted with explicit `data=ordered` (or XFS), compute mode default, no `fork()` after init, kernel/driver combination (this host reports Linux 7.0.0; nvidia-fs supports 7.0 from GDS 1.18; SGL-capable NVMe drives have a known issue in nvidia-fs mode on 6.17+; kernels 6.11+ regress small GDS IO). If any check fails, or on Grace, start with the host path: it reached 25.8 GB/s versus 26.4 GB/s for GDS on four 7 GB/s drives (fastsafetensors) and saturated a 12 GB/s RAID0 with 4 cores and O_DIRECT (ServerlessLLM).
10. **If you control the parquet files, fix the layout.** Row groups of about 4M rows or more (DaMoN'26 used 10M) bring column chunks to MiB scale, which let one SSD saturate under GDS; the paper's full rewrite (page count of 100 or more for decode parallelism, large row groups, Parquet V2 encodings, no unnecessary compression) took four SSDs to 125 GiB/s effective bandwidth, of which the row-group step alone reached 45 GiB/s (Fig. 1). Default writers' ~100 KB column chunks sit in the regime where GDS is weakest. Where you do not control files, project contiguous columns and let the planner merge them.
11. **Direct libcufile versus kvikIO's `cuFileAPI` shim: prefer direct `cufile.h` plus a dlopen wrapper you own.**
    What the shim adds or hides (all [SOURCE-CODE], kvikIO main):
    - Lazy process-wide singleton: `cuFileAPI::instance()` (`cpp/src/shim/cufile.cpp`) `dlopen`s `libcufile.so.0` with `RTLD_LAZY | RTLD_LOCAL | RTLD_NODELETE` (`load_library`, `cpp/include/kvikio/shim/utils.hpp`/`cpp/src/shim/utils.cpp`) and resolves every symbol in the constructor with `get_symbol`, which throws `std::runtime_error` on any missing symbol. The constructor comment says CUDA 12.2 / cuFile 1.7.0.49 added the batch/async/stream symbols, so, by inference from the throwing `get_symbol`, a pre-1.7 library makes the whole shim unavailable (all-or-nothing); in AUTO mode kvikIO then falls back to POSIX.
    - Version gating: `cuFileGetVersion` if available, else assumes 1070; `cufile_version()` returns 0 if the library is missing. No per-call feature gating seen in `file_handle.cpp`.
    - Availability and compat detection: `is_cufile_available()` = library loads and `/run/udev` is a directory (`run_udev_readable`) and `uname` release does not contain "icrosoft" (WSL). AUTO resolves once, process-wide, to OFF or ON (`defaults::infer_compat_mode_if_auto`). Per handle: O_DIRECT open failure or `cuFileHandleRegister` error in AUTO silently switches that handle to POSIX (`CompatModeManager`). Async is treated as unavailable (sync read after stream sync) when no cuFile config file is found (`config_path()` checks `CUFILE_ENV_PATH_JSON` then `/etc/cufile.json`; `cpp/src/cufile/config.cpp`).
    - Driver lifecycle: `DriverInitializer` opens the driver at first use and closes it at static destruction, swallowing exceptions (`cpp/src/cufile/driver.cpp`); no stdin guard or `_v2` selection seen in what I read (not exhaustively verified).
    - Handle plumbing: two fds per file (buffered and O_DIRECT, both `O_CLOEXEC`), only the O_DIRECT fd registered (`CU_FILE_HANDLE_TYPE_OPAQUE_FD`, `cpp/src/file_utils.cpp`), CUDA context push/pop around cuFile calls on worker threads (`PushAndPopContext`), `StreamFuture` with malloc'ed async arguments.
    - Not provided: stream registration, default buffer registration, `cuFileSetParameter*`, batch API use, any real readiness probe, any request planner for local files.

    What to reproduce, and only that:
    1. A lazy `dlopen("libcufile.so.0")` with per-symbol `dlsym` where optional symbols (async, stream, batch, parameter set/get, `cuFileDriverClose_v2`) are treated as "feature unavailable", never as total failure; version gates from the release notes (async/stream and non-O_DIRECT fds: 1.7 / CUDA 12.2; NVMe P2PDMA: 1.13; scatter-gather: 1.19; CUDA graphs are a documented non-goal for the stream APIs).
    2. `cuFileSetParameter*` first, then one `cuFileDriverOpen`; prefer `cuFileDriverClose_v2` (reference counted per DALI's source comment, so cuDF/kvikIO in the same process is not broken; the Ubuntu `cufile.h` man page shows `cuFileDriverClose` defined as the `_v2` symbol); DALI's stdin guard (dup before, dup2 after if fd 0 vanished); explicit shutdown before CUDA teardown; do not enable `cufile_stats` with a dl-opened library on CUDA older than 13.0 (kvikIO #497, release notes).
    3. Your own handle cache keyed by (device, inode) with reference counts (item 8), O_DIRECT open with host-path fallback.
    4. A real startup probe instead of the `/run/udev` and WSL heuristics: register a handle on a file in the target file system, issue a 1 MiB `cuFileRead`, check the returned byte count, and inspect driver properties or cufile.log for compat mode; cache the verdict per mount.
    5. CUDA context discipline: make the primary context current on the reactor and I/O threads before cuFile calls (NVIDIA: use the primary context; cuFile's internal workers call `cuDevicePrimaryCtxRetain`, forum 295318).
    6. Stable storage for async `size`/`file_offset`/`bytes_read` until the stream completes (what `StreamFuture` does).

    Why direct is better here: the shim hides exactly the settings NVIDIA says matter (stream registration flags, parameter API, buffer registration), its all-or-nothing symbol loading and static driver lifecycle sit awkwardly with a long-lived reactor (its dlopen pattern exposed an exit-time cuFile crash, #497, a cuFile defect fixed in CUDA 13.0), its compat and threshold logic duplicates or fights your planner, and a double open/close hazard appears if cuDF's kvikIO and your reactor both drive the process-wide driver. Keep kvikIO only if you also want its POSIX/remote paths; this reactor already has its own POSIX fallback. [INFERENCE]
12. **What not to import from kvikIO.** Its defaults (1 thread, 4 MiB tasks, 16 KiB threshold, 16 MiB bounce), its per-task unpipelined bounce loop, and its benchmark numbers are low-confidence evidence about cuFile; use the NVIDIA documentation and the direct-user and measurement evidence above instead. [LOW-CONFIDENCE: kvikIO]
