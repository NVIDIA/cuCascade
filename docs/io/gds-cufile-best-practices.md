# cuFile / GPUDirect Storage best practices (research dossier for the cuCascade cuFile reactor)

> **Status.** Research dossier compiled 2026-10-14 from NVIDIA's GDS documentation (v1.19.1), headers, release notes, NVIDIA-authored sample/library source, GitHub issues and forum threads. Nothing here was verified on GDS hardware: the development hosts run cuFile in compatibility mode only. Every claim carries one tag (`[DOC]`, `[MEASURED]`, `[INFERENCE]`, `[LOW-CONFIDENCE: kvikIO]`). The key quotes behind the recommendations were re-checked verbatim against NVIDIA's pages on 2026-10-15 (see the addendum at the end). For the actionable conclusions read [gds-reactor-recommendations.md](gds-reactor-recommendations.md); for other systems' experience read [gds-field-experience.md](gds-field-experience.md).


Prepared 2026-10-14 for the cuCascade `gds` worktree. Scope: how to use `cuFileHandleRegister` + `cuFileReadAsync` (stream API, unregistered device destination, POSIX `pread` fallback for small reads) correctly and fast on local NVMe, on libcufile 1.17.1 (CUDA 13.2), targeting H100/GB300-class production hosts. No file in the git repository was modified; all downloaded material lives in the session scratchpad.

## 0.5 Ten key findings (details and citations in the numbered sections)

1. **No NVIDIA source defines what happens when two threads call `cuFileReadAsync` on the same CUDA stream.** The only statement is "All APIs are thread-safe" (API §3). Every NVIDIA async sample drives each stream from one host thread, and the docs list "Needs multiple streams to submit in parallel" as a con. Your `cufile_async.h putStreamOp: Assertion tmp == sinfo` abort is not documented anywhere I could find. Rule to adopt: one stream per in-flight read slot, never two threads submitting into the same stream without a per-stream mutex (section 1.3).
2. **NVIDIA explicitly recommends NOT registering a single-use destination buffer** ("the registration cost will not be amortized"; BAR exhaustion). That contradicts "register temporarily per transfer for large I/O". Registration is "expensive ... can take up to a few milliseconds", 64 KiB-granular, and must be done "up front and off the critical path" (section 2).
3. **The unregistered path is a first-class, documented path** (pre-registered internal GPU bounce buffers + one extra D2D copy); NVIDIA improved it in 1.13 (threadpool for large IO, bounce buffers up to 16 MiB). Defaults changed in 1.17 to slab-based bounce buffers (1/8/16/64 MiB; 384 MiB per GPU). It is only "not performant for small IO sizes" (API §3.2) (section 2.5).
4. **RMM's default allocation alignment is 256 B** (`CUDA_ALLOCATION_ALIGNMENT{256}`), but cuFile direct DMA needs the device pointer (base + offset), file offset and size all 4 KiB-aligned; otherwise the IO silently goes through the bounce-buffer path even if you register the buffer. GPU BAR mappings are 64 KiB-granular, so 64 KiB alignment is the safe target (sections 2.4, 3.1).
5. **The stream API is the slowest documented way to read small/medium blocks**: "Higher execution latency for IO size (<1 MB)", measured ~149 us async vs ~72 us sync at 4 KiB, and a stream serializes its own operations (queue depth 1 per stream). Its worker pool is `execution.max_io_threads` (default 4 per GPU) with `max_io_queue_depth` 128; one unresolved NVIDIA issue shows async reads failing with `-5` once ~134 are outstanding. NVIDIA's own consumers (cuDF, NIXL) use synchronous `cuFileRead` from a thread pool, or the batch API, not the stream API (sections 1.4-1.6).
6. **Compat-mode fallback is silent and common.** Top causes: ext4 mount options not showing `data=ordered` explicitly, nvidia-fs/P2PDMA not active, unsupported fs/open flags. Detect via `cufile.log` ("using cuFile posix read/write with compat mode enabled"), `gdscheck.py -p/-f`, `cuFileGetStatsL3` per-GPU `n_posix_reads` vs `n_p2p_reads`, `/proc/driver/nvidia-fs/stats`; set `allow_compat_mode=false` to make fallback loud (section 5.1).
7. **Topology dominates everything**: on the NVIDIA DGX-2 benchmark, a GPU not under the NVMe's PCIe switch cut 1 MiB read throughput by 40% (6.52 to 3.89 GiB/s, latency 1.2 to 2.0 ms) and 4 KiB random-read IOPS from ~850k to ~28k (section 4.5, 6).
8. **Small IO and GDS**: NVIDIA documents a performance regression for IO <= 128 KB on kernels >= 6.11 (nvidia-fs and p2pdma paths), needs 64-128 threads for 4 KiB random reads, and shows GDS == CPU path when a single drive is the bottleneck (3.23 vs 3.19 GiB/s). No NVIDIA document sets a 1 MiB GDS-vs-POSIX cutoff for local NVMe (sections 3.4, 6, 7).
9. **Config facts for 1.17+**: uniform bounce-buffer parameters are deprecated for `gpu_bounce_buffer_slab_config`; the default `max_direct_io_size_kb` is now derived from the slabs (a GH200 `gdscheck` shows 1024 KB) and "To retain the previous 16 MiB maximum direct I/O chunk size, set max_direct_io_size_kb to 16384" (REL). Pinned budget: `maximum_pinned_memory = cache_size + user_registered_gpu_buffers` (MagnumIO maintainer, MIO-27); default cap 32 GiB (section 4.1).
10. **Hygiene/pitfalls**: one handle per fd (shareable across threads); `cuFileHandleRegister` rejects fds opened with `O_APPEND/O_NOCTTY/O_NONBLOCK/O_DIRECTORY/O_NOFOLLOW/O_NOATIME/O_TMPFILE`; cuFile's internal worker threads call `cuDevicePrimaryCtxRetain` (EXCLUSIVE_PROCESS compute mode makes them assert); no `fork()`; deregister buffers before `cudaFree` (documented nvidia-fs deadlock otherwise); cuFile-level errors can surface as `-1` with the `CUfileOpError` in `errno` (NVIDIA NIXL comment) (section 5).

## 1. Which API to use when

### 1.1 NVIDIA's own decision table

**[DOC]** BP §4 "Table 4.1 cuFile API Use Cases" (verbatim cells):

| API family | IO behavior | NVIDIA "Use Case" | Pros / Cons as written |
|---|---|---|---|
| `cuFileRead` / `cuFileWrite` | "Synchronous submission / Synchronous completion" | "Single-threaded application using standard file system calls for a single large file and large buffers (>16MB)" | Pro: "Simple to use". Con: "Does not help for multiple buffers" |
| same, "cuFile Threadpool enabled" | "Synchronous submission / Synchronous completion" | "Single-threaded application using standard file system calls for a single large file and large buffers. Multi-threaded application using standard file system calls for multiple files and buffers. Application has thread pools for its IO pipeline." | Pros: "Simple to use", "Lower submission latency", "Better for medium-sized IO requests of 64K and above." Cons: "Scalability limited by number of CPU threads used.", "Higher CPU cost for smaller IO sizes (4k-64k)." |
| `cuFileBatchIOSetup/Submit/GetStatus` | "Synchronous submission / Asynchronous completion" | "Single-threaded application using standard filesystem calls that performs IO for multiple non-contiguous file offsets, sizes, and GPU buffers. Each IO request is small (< 64KB). Can track completion of IOs asynchronously or wait in the same thread." | Pros: "Lower average completion latency", "Lower CPU cost because of batch submission". Cons: "Higher submission latency, can be reduced by partial submission", "More complex to code: submit followed by polling for completion of the batch" |
| `cuFileStreamRegister` + `cuFileReadAsync`/`WriteAsync` + `cuFileStreamDeregister` | "Asynchronous submission / Asynchronous completion" | "Single threaded application using standard file system calls for multiple non-contiguous file offsets, sizes and GPU buffers. IO sizes - buffer data is dependent upon prior CUDA work." | Pros: "Simple to use for CUDA developers", "Works with CUDA semantics: fire and forget.", "Lower submission latency". Cons: "Higher execution latency for IO size (<1 MB)", "Needs multiple streams to submit in parallel.", "Higher CPU utilization if synchronizing periodically." |

**[INFERENCE]** Reading the table against the reactor: its use case (many independent reads, each destined for an allocation that is not "dependent upon prior CUDA work", multi-threaded reactor) maps to row 2 (sync `cuFileRead` + your own thread pool), not row 4. The stream API's only unique value is ordering the IO inside a CUDA stream relative to other GPU work; if the reactor already synchronizes on completion with host-side events, that value is unused while the con list applies in full.

### 1.2 Stream API: semantic rules that are actually documented

All **[DOC]** unless marked.

* **Ordering.** API §5.4.3: "Operations that are enqueued with cuFile Stream APIs are FIFO ordered with respect to other work on the stream and must be completed before continuing to the next action in the stream." **[INFERENCE]** Consequence: one stream = at most one cuFile IO in flight. Queue depth = number of distinct streams (BP agrees: "Needs multiple streams to submit in parallel.").
* **Context.** API §5.4.3: "The current context of the caller is assumed." API §5.2: "The device pointer addresses referred to in these APIs pertain to the current context for the caller." BP §4: "APIs with GPU buffers should be called in a valid CUDA context." Every NVIDIA sample calls `cudaSetDevice(gpu)` in the submitting thread (SMP).
* **When arguments are read.** API §5.4.3: "Unless otherwise specified through `cuFileStreamRegister` API, file offset, buffer offset or size parameter will not be evaluated until execution time. In these scenarios, size parameters should be set to the maximum possible I/O size at the time of submission and can be set to the actual size prior to the stream I/O execution." So with registration flag 0 the three `*_p` arguments are pointers that must stay valid and hold final values until the stream reaches the IO.
* **Result slot.** API §5.4.3: "`bytes_read_p` ... This pointer should be a non NULL value and `*bytes_read_p` set to 0. After successful execution of the operation in the stream, the value `*bytes_read_p` will contain either: The number of bytes successfully read. -1 on IO errors. All other errors return a negative integer value of the `CUfileOpError` enum value." and "The `bytes_read_p` memory should be allocated with `cuMemHostAlloc`/`malloc`/`mmap` or registered with `cuMemHostRegister`. The pointer to access that memory from the device can be obtained by using `cuMemHostGetDevicePointer`." **[INFERENCE]** The device-pointer remark suggests the library writes the result from the GPU side; for the reactor, keep result slots in pinned host memory (cudaHostAlloc) to be safe on PCIe-attached (non-ATS) hosts. On GB300 (ATS/C2C) pageable memory is device-accessible, but that is an untested assumption here.
* **Submission returns before the IO runs, so failures surface late.** `cuFileReadAsync` returns `CU_FILE_SUCCESS` "on a successful submission" (API §5.4.3). IO errors appear only in `*bytes_read_p` after the stream is synchronized. **[MEASURED]** MIO-18: `cuFileReadAsync` kept returning `CU_FILE_SUCCESS` while `read_bytes_done` became `-5` once the batch of async ops exceeded 133 ("MAX_BATCH_SIZE 133 is the golden value to pass, 134 will fail"); unresolved. **[INFERENCE]** 133/134 is suspiciously close to `execution.max_io_queue_depth` = 128 ("maximum number of pending work items that can be held by the cuFile library's internal threadpool sub-system", CFG Table 4.2). Cap outstanding stream IOs below that setting (and raise the setting if you need more).
* **Stream registration (optional).** BP §4.6: "Explicit stream registration with the cuFileStreamRegister API is optional. If the stream is registered, then some internal buffers and associated metadata resources will be pre-allocated for subsequent stream I/O and may improve I/O latencies. Additionally these resources will be reused until deregistered ... Without this API, all these resources will be allocated during actual I/O." API §5.4.1: "The API will synchronize on the stream before allocating resources." Flags (API §5.4.1): `0x0` "All the I/O parameters are valid only at the time of execution."; `0x1` "Buffer offset value is valid at submission time."; `0x2` "File offset value is valid at submission time."; `0x4` "Size is valid at submission time."; `0x8` "All inputs i.e. buffer offset, file offset and size are 4K aligned."; `0xf` "All inputs are aligned and known at submission time" with the note "Using the flag 0XF will perform best as the workflow can be optimized during submission time." BP IO Pattern 7 uses a macro `CU_FILE_STREAM_FIXED_AND_ALIGNED`; **[DOC]** it is not in the 1.17.1 `cufile.h` (which defines `CU_FILE_STREAM_FIXED_BUF_OFFSET 1`, `..._FIXED_FILE_OFFSET 2`, `..._FIXED_FILE_SIZE 4`, `..._PAGE_ALIGNED_INPUTS 8`); the MagnumIO sample defines it itself as the OR of the four (= 15).
* **Teardown.** HDR (`cuFileStreamDeregister`): "must be called before cuStreamDestroy call for the specified stream"; "highly recommend to call after cuda stream errors to release any outstanding cuFile resources for this stream". `cuFileReadAsync`: "on cuda stream errors, the user must call cuFileStreamDeregister to release any outstanding cuFile resources for the stream." API §5.4.2: "The stream will be automatically deregistered as part of `cuFileDriverClose`." BP §4.7: "Before calling this API, the application must ensure that the I/O on that stream has completed and the stream is no longer being used".
* **Null stream.** API §5.4.3: "If NULL, make this operation synchronous." (and `cuFileStreamRegister`: "If NULL, make this operation in the default CUDA stream").
* **Unsupported combinations.** REL §11: "CUDA graphs are not supported with cuFile Stream APIs." "cuFile Stream APIs for GPFS and WekaFS are supported in compatibility mode only." "cuFile Stream APIs are not supported when cuFile configuration parameter `execution.parallel_io` is false or `execution.max_io_threads` is set to 0." and "`CU_FILE_STREAMS_SUPPORTED` bit is not set in `Props.fflags` when queried with `cuFileDriverGetProperties`" (listed under the same bullet). REL v1.7: "Threadpool support is enabled by default and is required for cuFile APIs supporting CUDA streams." TRB §5.17: "There could be many reasons for which stream based async I/O can fail. This will be logged in cufile.log. One of the common reasons could be that the internal thread pool is not enabled. Refer to cufile.json "execution" section on how to enable it."
* **How to test support at runtime.** **[DOC]** NVIDIA's sample tests flags as bit indices: `props.nvfs.dcontrolflags & (1 << CU_FILE_USE_POLL_MODE)` (SMP `1_cuFile_Basics/error_and_properties.cc`). **[INFERENCE]** By the same convention, streams are supported iff `props.fflags & (1u << CU_FILE_STREAMS_SUPPORTED)` after `cuFileDriverGetProperties`; gate the stream path on it and fall back to sync `cuFileRead`.
* **Compat mode.** **[DOC]** API §3.3 table: "cuFile Stream and cuFile Batch APIs on IBM Spectrum Scale or WekaFS: All Async and batch operations will internally use compatibility mode IO." **[MEASURED]** An Nsight Systems capture of a gdsio async run (A100; GDS-vs-compat not established by the poster) shows cuFile's own CUDA kernels (`cuFileSparseGPU`, `cuFileCopyGPU`) and `cuFileStreamSubmitIo` on the GPU timeline (FRM https://forums.developer.nvidia.com/t/understanding-the-latency-of-4k-read-workload-in-gdsio/339782); no NVIDIA doc describes the internal mechanism, and a related parameter `CUFILE_PARAM_STREAM_MEMOPS_BYPASS` exists in the 1.17.1 header (line 815) and API §4.1.1 with no description anywhere.

### 1.3 Thread-safety statements and the same-stream question

**[DOC]** The complete set of NVIDIA statements:
* API §3: "All APIs are thread-safe." OVR §1.2.2.2: "All APIs are thread safe." BP §4: "The cuFile APIs are designed to be thread safe."
* BP §4.2: "There should be only one handle created for each file descriptor. ... The same handle can be shared by multiple threads."
* BP §4.3 (table): "A cudaContext must be established in each thread before registering the GPU buffers."
* BP §4 / API §3 / REL §11: no `fork()` after library init.
* OVR §1.2.2.2: "GDS does not boost concurrency, so this level of performance tuning is managed by the application."

**[DOC]** Nothing says what happens if two threads submit `cuFileReadAsync` into the **same** stream, nor whether stream registration state is protected against that. I searched all ten guides, the 1.17.1 header, NVIDIA samples, GitHub issues (gds-nvidia-fs, MagnumIO) and the NVIDIA developer forums; no result mentions `putStreamOp`, `sinfo`, or `cufile_async.h` (search-engine queries for those strings returned nothing relevant).

**[DOC]** What NVIDIA's own sample does: `4_cuFile_Async/async_rw_batch_register_custom.cc` submits N reads, each into its **own** stream (`cudaStreamCreateWithFlags(&io_stream[i], cudaStreamNonBlocking)`, `cuFileStreamRegister(io_stream[i], 15)`), all from the single main thread, with the comment "NOTE: One could create a single stream as well for all I/Os". No NVIDIA sample submits from several threads into one stream; NVIDIA staff on a related question: "Unfortunately, we do not have any multi-threaded samples" (FRM https://forums.developer.nvidia.com/t/getting-the-best-performance-from-nvidia-gpudirect-storage-apis-batch-io/256021, NVIDIA staff `rmitra`, 2023-06-21).

**[DOC] (NVIDIA staff, forum)** Evidence that cuFile aborts the whole process on internal invariant violations rather than returning an error: https://forums.developer.nvidia.com/t/cufilethreadpoolworker-run-assertion-0-failed/295318 : `python: cufile_worker_thread.h:57: virtual void CUFileThreadPoolWorker::run(): Assertion 0 failed`. NVIDIA's diagnosis (`prashantp`): "it looks like the cuda device is not available at this time and as a result the cuDevicePrimaryCtxRetain cuda call fails." (compute mode `EXCLUSIVE_PROCESS`; resolved by `CU_COMPUTEMODE_DEFAULT`). Same assertion family as your abort, different cause.

**[INFERENCE]** The assertion text `tmp == sinfo` in `putStreamOp` reads like "the stream-info record I just looked up/removed is the record I expected". That is what you would see if a per-stream bookkeeping structure (keyed by stream handle, created by `cuFileStreamRegister` or lazily on first use) is mutated by two submitters at once, or if a stream is deregistered/destroyed while ops are queued. The docs' global "thread-safe" claim evidently does not extend to concurrent submission into one stream. **Adopt as a hard rule:** (a) one stream per in-flight read slot, or (b) a per-stream mutex held across the `cuFileReadAsync` call, and never `cuFileStreamDeregister`/`cudaStreamDestroy` while ops are outstanding. A 20-line stress test (2 threads, one stream, N iterations, with and without a mutex, with and without `cuFileStreamRegister`) will settle it on a machine where the abort reproduces (section 10, Q1).

**[DOC] (NVIDIA staff, forum) on concurrent batches:** "If you want to submit multiple batches in parallel, I would suggest to use multiple threads each performing one batch I/O ... each threads will be performing I/Os (submit + wait until done) operating on their individual set of parameters" (same thread as above). **[MEASURED]** (same thread, user data, 2023, CUDA 12.1-era GDS 1.6.x, 2x RTX A5000, one Samsung PM983 NVMe): submitting 8 batches of 128 x 4 KiB reads from 8 threads was slower than from one loop (30.6 ms vs 5.8 ms total for 4 MB), the poster saw threads "stalling at cuFileBatchIOSubmit" and suspected an internal lock; NVIDIA did not reply to that last message. Treat batch submission as not scaling with submitter threads on old versions.

### 1.4 Per-API overheads that NVIDIA states or that were measured

* **[DOC]** OVR §1.2.2.4: "There is a fixed overhead involved with each submission from an application into the cuFile implementation. For usage models where many IO transactions get submitted simultaneously, batching reduces the overhead by amortizing that fixed overhead across the transactions in the batch, which improves performance."
* **[DOC]** TRB §16.13/§17.13: "It has been observed that m separate batches with n/m entries each, showed better performance than 1 batch with n entries especially in case of NVMe based storage."
* **[DOC]** BP Table 4.1: stream: "Lower submission latency" but "Higher execution latency for IO size (<1 MB)"; threadpool sync: "Higher CPU cost for smaller IO sizes (4k-64k)."

### 1.6 What NVIDIA's own consumers of cuFile do (useful as the reference design)

* **[MEASURED] / [DOC]** NVIDIA cuDF (B3, 2022, DGX-2, single V100, RAID0 of two 3.84 TB NVMe, GDS 1.2): "We found that the read bandwidth is not saturated when these operations are performed in a single thread, leading to suboptimal performance regardless of GDS use." "As of version 1.2.1.4, cuFile calls are synchronous, so parallelism requires multithreading from downstream users." "We discovered that the highest end-to-end read throughput was for 8-32 threads and 1-16 MiB slice size." Design: a thread pool slices each large read into fixed-size slices, each worker making a **synchronous** `cuFileRead`. "Small slice sizes cause higher overhead due to the large number of read tasks, and large slice sizes lead to poor utilization of the thread pool."
* **[DOC]** NIXL (NVIDIA Inference Xfer Library), GDS backend, default `mode=batch`: preallocates a **pool of 16 cuFile batch handles** (`batch_pool_size=16`), each `cuFileBatchIOSetUp(&h, 128)` (`batch_limit=128`), splits every transfer into chunks of at most 16 MiB (`max_request_size=16777216`), and never creates batches on the data path ("Pool exhausted - don't create new batches in the data path"; `gds_batch_engine.cpp`). Alternative `mode=mt`: persistent worker threads, "one `cuFileRead` or `cuFileWrite` per prepared request" (README), default `max(1, hardware_concurrency/2)` threads. Neither mode uses the stream API. File handles are cached per fd (`gds_file_map_`, one `cuFileHandleRegister` per fd); buffer registration happens once at memory-registration time and failure is non-fatal ("buffer registration failed - will use compat mode"); the batch path treats any entry that completes with `ret != size` as an error ("GDS batch entry completed X of Y bytes"), as does the MT path ("short read").
* **[INFERENCE]** Two NVIDIA-authored production consumers, written years apart, converge on: synchronous `cuFileRead` from many threads over shared handles, or pooled batch handles; 1-16 MiB request granularity; handle caching; no per-IO registration; no stream API.

## 2. Buffer registration (`cuFileBufRegister`)

### 2.1 What it does and what it costs

* **[DOC]** BP §4.3: "GPU buffers need to be exposed to third-party devices to enable DMA by those devices. The set of pages that span those buffers in the GPU virtual address space need to be mapped to the Base Address Register (BAR) space, and this mapping is an overhead. ... Explicit GPU buffer registration with the cuFileBufRegister API is optional. If a user buffer is not registered, an intermediate pre-registered GPU buffer that is owned by the cuFile implementation is used, and there is an extra copy from there to the user buffer."
* **[DOC]** API §4.5: "The cuFileBufRegister API incurs a significant performance cost, so registration costs should be amortized where possible. Developers must ensure that buffers are registered up front and off the critical path." and "The cuFileBufRegister API is optional. If this is not used, instead of pinning the user's memory, cuFile-managed and internally pinned buffers are used."
* **[DOC]** TRB §7.6: "The cuFileBufRegister function makes the pages that underlie a range of GPU virtual memory accessible to a third-party device. This process is completed by pinning the GPU device memory in the BAR space, which is an expensive operation and can take up to a few milliseconds." The sample bcc/funclatency histogram in the same section shows `nvidia_p2p_get_pages` calls of 262,144-1,048,575 ns (0.26-1.05 ms) for 8 registrations. TRB §5.12: "The pinning and unpinning of GPU memory through cuFileBufRegister and cuFileBufDeregister is an expensive operation. If you notice a large number of registrations (n) and deregistration (free) in the nvidia-fs stats, it can hurt performance."
* **[DOC]** HDR (`cuFileBufRegister`): "@warning This API is intended for usecases where the memory is used as streaming buffer that is reused across multiple cuFile IO operations before calling cuFileBufDeregister".
* **[DOC]** The kernel API underneath (RDMA doc §3.1): "The most straightforward implementation using GPUDirect RDMA would pin memory before each transfer and unpin it right after the transfer is complete. Unfortunately, this would perform poorly in general, as pinning and unpinning memory are expensive operations. ... Hence, lazily unpinning memory is key to a high performance RDMA implementation."
* **[DOC]** Host-side cost: BP §3.3: the property `max_direct_io_size_kb` "defines the additional system memory that is used for each buffer during cuFileBufRegister up to a maximum value ... of 16MB. This value can be reduced to 1MB to lower the amount of system memory that is used per buffer." Example in the same section: 256 threads each registering a 1 MB buffer gives `Active Shadow-Buffer (MB): 256` in `/proc/driver/nvidia-fs/stats`.
* **[DOC]** What may fail: API §5.3.1: `CU_FILE_CUDA_MEMORY_TYPE_INVALID` "for device memory that is not allocated via cudaMalloc or cuMemAlloc"; `CU_FILE_INVALID_MAPPING_SIZE` "if the size exceeds the GPU resource limits"; `CU_FILE_GPU_MEMORY_PINNING_FAILED` "if not enough pinned memory is available"; `CU_FILE_MEMORY_ALREADY_REGISTERED`; `CU_FILE_CUDA_POINTER_RANGE_ERROR` "if the size exceeds the bounds of the allocated memory". The `flags` argument: API "Reserved for future use; must be 0."; HDR documents `CU_FILE_RDMA_REGISTER`; NVIDIA staff (forum, `kmodukuri`, 2024-03): "CU_FILE_RDMA_REGISTER if set to 1 will be used to pre register the buffers for use with RDMA. This is useful for Weka and GPFS mounts. ... This flag should not be used if the application is used with Lustre, NFS, BeeGFS or NVMe mounts." Pass 0 for local NVMe.

### 2.2 When registration pays (NVIDIA's table) and what it says about "register per transfer"

**[DOC]** BP §4.3 table (verbatim):

| Use Case | Description | Recommendation |
|---|---|---|
| "A 4KB-aligned GPU buffer is reused as an intermediate buffer to read or write data using optimal IO sizes for storage systems in multiples of 4KB." | "The GPU buffer is used as an intermediate buffer to stream the contents or to populate a different data structure in GPU memory." | "Register this reusable intermediate buffer to avoid the additional internal staging of data by using GPU bounce buffers in the cuFile library." (IO Pattern 2) |
| "Filling a large GPU buffer for one use." | "The GPU buffer is the final location of the data. Since the buffer will not be reused, the registration cost will not be amortized. A usage example is reading large preformatted checkpoint binary data. Registering a large buffer can have a latency impact when the buffer is registered. This can also cause BAR memory exhaustion because running multiple threads or applications will compete for BAR memory." | "Read or write the data without buffer registration." (IO Pattern 3) |
| "Partitioning a GPU buffer to be accessed across multiple threads." | "The main thread allocates a large memory buffer and creates multiple threads. Each thread registers a portion of the memory buffer independently ... You can also register the entire buffer in the parent thread and use this registered buffer with the size and devPtr_offset parameters set appropriately with the buffer offsets for each thread. A cudaContext must be established in each thread before registering the GPU buffers." | "Allocate, register, and deregister the buffers in each thread independently for simple IO workflows." (IO Pattern 6) |
| "GPU offsets, file offsets, and IO request sizes are unaligned." | "IO reads or writes are mostly unaligned. An intermediate aligned buffer might be needed to handle alignment issues with GPU offsets, file offsets, and IO sizes." | "Do not register the buffer." (IO Patterns 4, 5) |
| "Working on a GPU with a small BAR space as compared to the available GPU memory." | "In some GPU SKUs, the BAR memory is smaller than the total device memory." | "To avoid failures because of BAR memory exhaustion, do not register the buffer." |

**[DOC]** IO Pattern 1 (register + read + deregister inside the loop, 100 MB per iteration): "Although semantically correct, this loop might not provide the best performance because cuFileBufRegister and cuFileBufDeregister are continuously issued in the loop."

**[INFERENCE] Contradiction with the project constraint "CAN register temporarily per-transfer for large I/O".** NVIDIA's own table says the opposite for the reactor's typical case (a large read whose destination is the final home of the data): do not register; the cost is "not amortized", it adds latency, and with several threads/processes it competes for scarce BAR. A per-transfer register is only defensible when the same pinned range is then reused for many reads (e.g. a long streaming read into one staging buffer). Even then NVIDIA prefers registering once, up front.

### 2.3 BAR1: limits and how to query

* **[DOC]** TRB §6.4: "GDS uses BAR memory in the following cases: When the process invokes cuFileBufRegister. When GDS uses the cache internally to allocate bounce buffers per GPU." "There is no per-GPU configuration for cache and BAR memory usage." Per process: `max_device_cache_size` and `max_device_pinned_mem_size` "configuration is per process, and the configuration is set across all GPUs."
* **[DOC]** TRB §6.5: the bounce cache is lazy: "this does not mean that GDS pre-allocates 128 MB of memory per GPU up front. Memory allocation is done on the fly and is based on need. After the allocation is complete, there is no purging of the cache."
* **[DOC]** TRB §6.7: "If the application tries to pin memory beyond the available BAR space, the nvidia_p2p_get_pages API returns a -12 (ENOMEM) error code."
* **[DOC]** REL §11 (known limitation): "Available BAR1 memory reported by the nvidia-smi utility is not accurate due to some internal overhead of the CUDA toolkit. Therefore, a huge allocation of BAR1 memory by any GDS application can run into ENOMEM errors, even when nvidia-smi utility shows there is available BAR1 memory."
* **[DOC]** DES §6.3: "The transfer size might exceed the size of the current GPU BAR1 aperture. In such cases, the GPUDirect Storage software recognizes that, chunks the large transfers to fit, and uses an intermediate buffer in GPU memory for the DMA engine to copy into and the GPU to copy out of into the target buffer. This is handled transparently but adds some overhead. Increasing the GPU BAR1 size, or choosing a GPU with a larger maximum BAR1 size, can reduce or eliminate such copy overheads."
* **[DOC]** NVIDIA/MagnumIO maintainer (`ahoyle-nvidia`), MIO-27: "maximum_pinned_memory = cache_size + user_registered_gpu_buffers" (the sample had set only 128 MiB, which "was not enough given maximum pinned memory should be derived from the following equation"; "We were previously not accounting for cache size").
* **[DOC]** RDMA §3.5 (PCI BAR sizes): "The maximum BAR size available for GPUDirect RDMA differs from GPU to GPU. For example, currently the smallest available BAR size on Kepler class GPUs is 256 MB. Of that, 32MB are currently reserved for internal use. These sizes may change." "On some Tesla-class GPUs a large BAR feature is enabled, e.g. BAR1 size is set to 16GB or larger."
* **[DOC]** RDMA §4.1: `nvidia-smi -q` shows "BAR1 Memory Usage Total/Used/Free"; "GPU memory is pinned in fixed size chunks, so the amount of space reflected here might be unexpected. In addition, a certain amount of BAR space is reserved by the driver for internal use, so not all available memory may be usable via GPUDirect RDMA. Note that the same ability is offered programmatically through the nvmlDeviceGetBAR1MemoryInfo() NVML API."
* **How to query (all [DOC]):** `cuFileGetBARSizeInKB(gpuIndex, &kb)` (API §5.1.12, present in the 1.17.1 header line 1119); `gdscheck.py -p` prints per GPU "bar:1 bar size (MiB):N" or "bar:disabled" (TRB §3.2.2, §18.9); nvidia-fs stats per GPU `Registered_MiB` (BAR used by `cuFileBufRegister`), `Cache_MiB` (bounce cache), `max_pinned_MiB` (TRB §6.6, §18.2: "There is no way to monitor the BAR memory usage per process. However, GDS Stats tracks the global BAR usage across all processes."); NVML `nvmlDeviceGetBAR1MemoryInfo()`.
* **BAR sizes seen in `gdscheck` output** (**[DOC]** where from NVIDIA guides, **[MEASURED]** where from forum/GitHub logs): L4 32768 MiB (P2P, TRB sample); V100-SXM2-16GB 16384 MiB; A100-SXM4-40GB and A100-PCIE-40GB 65536 MiB (FRM logs); H100 80GB HBM3 131072 MiB (GH-74); H200 NVL 262144 MiB (GH-75); **RTX A5000 and RTX A6000 only 256 MiB** (FRM 234925, FRM 352258); **GH200: `bar:disabled bar size (MiB):N/A supports GDS`** (TRB §18.9 sample, GDS 1.17.0.44, aarch64). I found no NVIDIA-published BAR1 size for T4 or B300; query it (section 10, Q7).
* **[MEASURED]** (NVIDIA forum, 2025-11, https://forums.developer.nvidia.com/t/cufilebufregister-fails-above-256-mb-on-rtx-a6000-48-gb-hbm-with-error-5016-how-to-increase-the-maximum-registration-size/351408 ; same user's `gdscheck`: "RTX A6000 bar:1 bar size (MiB):256"): `cuFileBufRegister` works up to ~256 MB and fails above with 5016 (`CU_FILE_INVALID_MAPPING_SIZE`) regardless of `max_device_pinned_mem_size_kb=33554432`. **[INFERENCE]** The BAR1 aperture, not the config cap, was the limit; a 16 GiB BAR1 cannot hold a registration of a 60 GiB RMM pool, and even where BAR1 is large the default pinned cap is 32 GiB per process.
* **[DOC]** If BAR1 is small, NVIDIA says not to register and let the library chunk: HDR `cuFileRead` note: "This is also recommended for cases where the BAR1 memory size is smaller than the size of the allocated memory."

### 2.4 Alignment and granularity of registered ranges

* **[DOC]** RDMA §3.2: "As the GPU BAR space is typically mapped using 64KB pages, it is more resource efficient to maintain a cache of regions rounded to the 64KB boundary. Even more so, as two memory areas which are in the same 64KB boundary would allocate and return the same BAR mapping." RDMA §4.5: "As nvidia_p2p_get_pages() will need a pointer aligned to 64K ... as the BAR space is currently mapped in chunks of 64KB, it is more resource efficient to round the whole pinning to 64KB."
* **[DOC]** BP IO Pattern 4 and TRB §7.2 list the alignment conditions that force the bounce cache (4 KiB for file offset, size, `devPtr_base`, and `devPtr_base+devPtr_offset`).
* **[MEASURED]** (NVIDIA forum, DGX A100, GDS 1.0.2.10, https://forums.developer.nvidia.com/t/cufilebufregister-fails-for-some-buffer-sizes/242847): registering 96 KiB failed with 5030 (`CU_FILE_INTERNAL_ERROR`); the user found "sizes that are multiples of 64kb, as well as 64kb aligned device pointers are necessary for successful buffer registrations in my setup." No NVIDIA reply; old version.
* **[MEASURED]** (NVIDIA forum, 2025-10, `cuFileBatchIO fails with mixed IOs`, GDS 1.15, A10): entries "are classified as mixed I/Os because the device pointer offsets are not aligned to the GPU page size (64KB)" (poster's reading of the log).
* **[MEASURED]** (third party, IIT abstract above): for writes, requests >= 128 KB that "do not align perfectly in memory ... can cause several additional P2P DMA requests to be created ... This is due to the GPU page size being 64KB."
* **[INFERENCE]** Register whole `cudaMalloc`/`cuMemCreate` allocations (their granularity is >= 64 KiB, normally 2 MiB), never sub-ranges at odd offsets; for unregistered reads align the destination pointer and size to 64 KiB where you can and to 4 KiB at minimum.

### 2.5 The unregistered path (what cuFile does when you do not register)

* **[DOC]** BP IO Pattern 3: "Internally, GDS uses GPU bounce buffers to perform IOs. Bounce buffers are GPU memory allocations that are internal to GDS, and these buffers are registered and managed by the GDS library. The number of bounce buffers is capped based on the max_device_cache_size (representing the total size of the bounce buffer cache) and per_buffer_cache_size (representing the size of each buffer) setting in the /etc/cufile.json file. The default values for max_device_cache_size and per_buffer_cache_size are 128MB and 1MB respectively, which amounts to 128 bounce buffers in total by default."
* **[DOC] (1.17+)** CFG Table 4.2 and REL v1.17: `properties:gpu_bounce_buffer_slab_config:slab_size_kb` default `[1024, 8192, 16384, 65536]` and `slab_count` `[128, 8, 4, 2]` ("Values must be 4 KB aligned and in strictly increasing order. Include a slab size less than or equal to 16384 KB for nvidia-fs based I/O."); the uniform parameters (`max_device_cache_size_kb`, `per_buffer_cache_size_kb`, `max_direct_io_size_kb`) are now "legacy"; REL v1.17: "Added deprecation warnings for uniform bounce buffer configuration parameters and APIs." **[INFERENCE]** 128x1 MiB + 8x8 MiB + 4x16 MiB + 2x64 MiB = 384 MiB per GPU (= the `max_device_cache_size_kb : 393216` printed in the 1.17.0.44 GH200 `gdscheck` sample, TRB §18.9).
* **[DOC]** REL v1.13: "Improved unregistered buffer IO performance for larger IO size using threadpool." and "Improved unregistered buffer IO performance by increasing the internal bounce buffer size. The size can be configured up to a max of 16MiB using the JSON parameter per_buffer_cache_size_kb."
* **[DOC]** When the pool is used (CFG §4.3.2): "This pool is used when buffers are not registered, unaligned buffer or file offsets, and when the storage and GPU cross NUMA nodes (typically CPU sockets)." (In the gds_stats `PER_GPU POOL BUFFER STATS`.)
* **[DOC]** BP §3.2: the bounce-buffer D2D copies are posted "on a stream created on the primary CUDA context. If a heavy compute job or application kernel is running in the background in the form of GPU kernels on a separate context (not the primary context), it can interfere with the D2D copies and increase the D2D copy launch times. ... it is recommended that the application launch GPU kernels on the primary context." CFG: `io_priority` ("default", "low", "med", "high"): "Tuning this might be helpful in cases where cudaMemcpy is not performing as expected because of the GPU being consumed by the compute."
* **[DOC]** Failure mode: BP IO Pattern 5: "If the IO is unaligned, the cuFile library will issue IO through its internal GPU bounce buffer cache. However, if the allocation of the internal cache fails, the IO will fail. To avoid IO failure in this case, you can set allow_compat_mode to true".
* **[DOC]** Compat-mode cost: TRB §18.12.4: "Currently, in compatible mode, the IO path with non-registered buffers does not have optimal performance and does buffer allocation and deallocation in every cuFileRead or cuFileWrite." (the host `posix_pool_slab_*` pools; defaults 4/1024/16384 KiB x 128/64/64.) **[INFERENCE]** Benchmarks on the no-nvidia-fs host over-penalize unregistered buffers relative to a real GDS host.
* **[DOC]** "Not using cuFileBufRegister might not be performant for small IO sizes." (API §3.2).

### 2.6 Which allocators can be registered (cudaMalloc, cuMem*, cudaMallocAsync, RMM, managed)

* **[DOC]** OVR §1.1.2: "Ability to target memory that has been allocated with any of cudaMalloc or cuMemAlloc or cuMemCreate/cuMemMap to the GPU, or cudaHostAlloc or cudaMallocHost to the CPU. GDS peer-to-peer mode does not support migratable memory, allocated with cudaMallocManaged or system-allocated memory (malloc, stack, etc.) on systems where UVM support is available such as Grace-Hopper. GDS will support IO to these memory allocations using a compatible path using internal GPU/CPU bounce buffers." REL v1.5: "Added support for cuMem* memory allocations with cuFile APIs." TRB §4.4: `CU_FILE_CUDA_MEMORY_TYPE_INVALID` for `cudaMallocManaged` memory; "GDS indirectly supports cudaMallocManaged memory when the memory is used as an unregistered buffer with cuFileWrite and cuFileRead."
* **[DOC]** NVIDIA's `5_cuFile_MemMap` samples show `cuFileBufRegister` on `cuMemMap`-ed ranges; because a mapping can be resized they register the final expected VA range up front (the sample comments in `memmap_preregister.cc` say cuFile registers the expected resized device memory in advance, so no re-registration is needed) or re-register after resizing (`memmap_reregister.cc`). REL known issue: "The cuFileRead and cuFileWrite APIs fail when working on cuMemMap allocations with multiple GPUs, when the IO request to a GPU buffer is not 4K aligned and spans across multiple GPUs."
* **[DOC]** `cudaMallocAsync` (stream-ordered pool) memory: **not mentioned anywhere** in the cuFile docs. API §5.3.1's error text ("device memory that is not allocated via cudaMalloc or cuMemAlloc") suggests pool memory may be rejected. **[INFERENCE]** Do not assume `cuFileBufRegister` works on `cudaMallocAsync` or RMM `async_memory_resource` pointers; test (section 10, Q6). It is safe to use them as **unregistered** destinations (cuFile only needs a valid device pointer).
* **[DOC]** RMM pools: `bufPtr_base` for a registered buffer "must remain set to the base address used in the cuFileBufRegister call" (API §5.2.3) and the sub-range is addressed with `bufPtr_offset` ("This parameter should be used only with registered buffers"). So if you ever register an RMM pool's upstream block, issue `cuFileReadAsync(fh, block_base, &size, &file_off, &(p - block_base), ...)` for a sub-allocation `p`; for unregistered buffers pass `p` itself with offset 0. **[INFERENCE]** Registering an entire pool is almost never right: BAR1 size, `max_device_pinned_mem_size_kb` (default 32 GiB), registration time, and the dereg-before-free rule below.
* **[DOC] Dereg-before-free hazard.** REL §10 known issues: "nvidia-fs can deadlock in nv_p2p_dma_map_pages and nv_p2p_mem_info_free_callback functions when the user frees the CUDA memory without calling cuFileBufDeregister on registered buffers." TRB §18.1 (`Bar1-map callbacks`): the callback fires "When cudaFree is invoked on memory, which is pinned through cuFileBufRegister, but cuFileBufDeregister is not invoked." The kernel doc agrees (RDMA §3.3: the unpin callback runs "If the userspace program explicitly deallocates the corresponding GPU memory, e.g. cuMemFree, cuCtxDestroy ... before the third party kernel driver has a chance to unpin the memory", and "dead-locking or live-locking scenarios may arise"). **[INFERENCE]** A pool allocator that returns memory with `cudaFree`/`cudaFreeAsync` while a registration is live is exactly this hazard. Registration must be owned by the same RAII object that owns the allocation, and `cuFileBufDeregister` must precede the free.
* **[DOC]** Host buffers can be registered too (API §5.3.1 "or host memory for IO operations"; OVR: cuFile APIs "can now be used with system memory" since 1.7).

### 2.7 Cost/benefit threshold

* **[DOC]** No NVIDIA document gives a break-even size or count. The qualitative rule is "reused intermediate buffer: register; single-use destination: don't".
* **[DOC] Caching registrations across reads.** A registration lives until `cuFileBufDeregister` or `cuFileDriverClose`: API §3.1 "If this API is not called, the buffer and resources are implicitly freed when the driver is closed using cuFileDriverClose."; API §4.5: "CUDA currently has no analog to cuFileBufDeregister. The cleaning up of objects associated with the buffers operated on in the cuFile context occurs at cuFileDriverClose." (i.e., nothing frees it when the CUDA allocation is freed). NVIDIA's guidance for the same problem in the kernel API is the registration (pin-down) cache, RDMA §3.2: "Communication middleware often employs an optimization called a registration cache, or pin-down cache, to minimize pinning overhead ... implementing lazy unpinning, LRU de-registration ... In the CUDA environment, this is even more important as the amount of memory which can be pinned may be significantly more constrained than for host memory." and RDMA §3.1: "An example implementation of lazy unpinning would keep a set of pinned memory regions and only unpin some of them (for example the least recently used one) if the total size of the regions reached some threshold, or if pinning a new region failed because of BAR space exhaustion". The same section warns that such caches "usually rely on the ability to intercept deallocation events happening in the user application, so that they can unpin the memory". **[INFERENCE]** A cuFile registration cache for the reactor must be keyed by allocation base address, bounded by a BAR/pinned-memory budget, evict LRU entries on `CU_FILE_GPU_MEMORY_PINNING_FAILED`/`CU_FILE_INVALID_MAPPING_SIZE`, and be told about every free (hook the memory resource) so it can deregister first.
* **[INFERENCE]** Break-even model for a reusable staging buffer: registration costs R (order 0.3-1 ms for a few MiB per the funclatency sample; "up to a few milliseconds" in the text; grows with size) and saves, per read, one D2D copy of S bytes plus bounce-buffer management. At 1 TB/s device-copy bandwidth, a 16 MiB D2D copy costs ~16 us, so the saving per read is on the order of tens of microseconds to a few hundred; break-even is therefore on the order of tens of reads per registered buffer, i.e. **register only long-lived buffers that serve hundreds of reads or more**. For one-shot destinations the model never breaks even. (Measure with `gdsio -b`, which skips registration; section 10, Q3.)
* **[INFERENCE]** The reactor's option space, in order of preference: (1) no registration, 4 KiB/64 KiB-aligned destinations, 1-16 MiB reads (the NVIDIA-documented path for "reading large preformatted checkpoint binary data"); (2) a small number of long-lived registered staging buffers (e.g. N x 4-16 MiB) plus a D2D copy to the final destination if profiling shows the bounce-buffer path is the bottleneck; (3) per-transfer registration: not recommended.

## 3. I/O size, alignment and queue depth

### 3.1 Alignment rules and what happens when they are violated

* **[DOC]** BP IO Pattern 4 (the definition NVIDIA uses everywhere): "An IO is unaligned if one of the following conditions is true: The file_offset that was issued in cuFileRead or cuFileWrite is not 4K aligned. The size that was issued in cuFileRead or cuFileWrite is not 4K aligned. The devPtr_base that was issued in cuFileRead or cuFileWrite is not 4K aligned. The devPtr_offset that was issued in cuFileRead or cuFileWrite is not 4K aligned." TRB §7.2 repeats it and adds the observable: "If the cache_MB field is active on a GPU, GDS is using the cache internally to complete the IO."
* **[DOC]** What the library does: BP IO Pattern 4: "the GDS library will internally use GPU bounce buffers to complete the IO ... because the IO was unaligned, the GDS library cannot perform IO directly to these registered buffers. To handle unaligned IOs, the library will use GPU bounce buffers to perform the IO and copy the data from the bounce buffers to the application buffers. As a best practice, if the application typically performs unaligned IO, the application buffers do not need to be registered using the GDS library." "Unaligned IOs might not be optimal and should be avoided by reading the size value that is specified in multiples of 4KB and the file_offsets value that is specified in multiples of 4KB."
* **[DOC]** API §5.2.3: "The API works correctly for unaligned offsets and any data size, although the performance might not match the performance of aligned reads." §5.2.4 (write): "...although the performance is not on-par with aligned writes." BP: "When the write workload is unaligned, GDS uses Read-Modify-Write internally using POSIX mode." CFG: "Unaligned writes are generally sub-optimal, as they can require read-modify-write operations." (`fs.generic.posix_unaligned_writes`, section 4.1.)
* **[DOC]** OVR §1.3.2.2: "The alignment is handled at this level [libcufile], and there might be some performance impact, so that buffers do not need to be aligned". DES §5.4: "The transfer does not need to be aligned to anything other than a byte boundary." (That is a correctness statement; the performance statement is BP's.)
* **[DOC]** Observability: stats `Read.unalign/Write.unalign` = "Number of cuFileRead/cuFileWrite per GPU which have at least one IO parameter not 4K aligned. This can be either size, file offset or device pointer." (TRB Table 20.3); `CUfilePerGpuStats.n_unaligned_reads/_writes` (API §4.1.1, `cuFileGetStatsL3`).
* **[DOC] / [INFERENCE] RMM destinations are not 4 KiB-aligned by default.** RMM source: `static constexpr std::size_t CUDA_ALLOCATION_ALIGNMENT{256};` ("Default alignment used for CUDA memory allocation", RMM `aligned.hpp`). cuFile needs `devPtr_base + devPtr_offset` 4 KiB-aligned for direct DMA, so an arbitrary RMM sub-allocation (256 B-aligned) falls onto the **unaligned path (bounce buffer + copy) even if you register it**. Align at the allocation site (over-allocate by 4 KiB/64 KiB and align the pointer, keeping the raw pointer for deallocation), or read into an aligned staging region and copy. Count the damage with `n_unaligned_reads` (L3 stats) / `Cache_MiB` (nvidia-fs stats).
* **[DOC]** Linux side (needed for the POSIX `pread` fallback and for the O_DIRECT fd you hand to cuFile): LNX `open(2)`: "The O_DIRECT flag may impose alignment restrictions on the length and address of user-space buffers and the file offset of I/Os. In Linux alignment restrictions vary by filesystem and kernel version and might be absent entirely. The handling of misaligned O_DIRECT I/Os also varies; they can either fail with EINVAL or fall back to buffered I/O." "Since Linux 6.1, O_DIRECT support and alignment restrictions for a file can be queried using statx(2), using the STATX_DIOALIGN flag" (`stx_dio_mem_align`, `stx_dio_offset_align`). **[INFERENCE]** Use `statx(..., STATX_DIOALIGN)` once per file to learn the kernel's real requirement, and take `max(that, 4096)` as the minimum alignment for the cuFile path (64 KiB for the GPU-side pointer/size, section 2.4). Per-call alignment in upper layers is the right place to do this (it avoids per-call bounce), but it must include the **device pointer**, not just file offset/size.
* **[INFERENCE]** Cheapest safe pattern for an unaligned logical range `[off, off+len)`: read `[floor4k(off), ceil4k(off+len))` into a 4 KiB-aligned destination and expose the sub-range; for tiny logical reads (< 64 KiB) prefer the POSIX path with a pinned buffer and an H2D copy (the GDS path pays fixed per-IO costs, section 3.4).

### 3.2 Chunking: `max_direct_io_size_kb` and the 1.17 default change

* **[DOC]** BP §3.3: "For the requested IO size, GDS issues IO requests sequentially in chunks of reads/writes based on the max_direct_io_size parameter. Larger values of max_direct_io_size will result in a reduced number of calls to the IO stack and might result in higher throughput." API §5.1.5: default 16384 KB "because typically parallel-file systems perform better with bulk read/writes." JSON: "max IO chunk size (parameter should be multiples of 64K) used by cuFileRead/Write internally per IO request".
* **[DOC]** 1.17+: CFG Table 4.2: `properties:max_direct_io_size_kb` "16384 (legacy/commented) ... In slab mode, this value is set automatically based on the configured slabs." REL §10: "To retain the previous 16 MiB maximum direct I/O chunk size, set max_direct_io_size_kb to 16384 in cufile.json." The 1.17.0.44 `gdscheck -p` sample on GH200 prints `properties.max_direct_io_size_kb : 1024` (TRB §18.9).
* **[INFERENCE]** On libcufile 1.17.x with default slabs, one large `cuFileRead` may be issued to the filesystem in 1 MiB chunks rather than 16 MiB. For sequential multi-MiB reads, explicitly set `max_direct_io_size_kb=16384` (multiple of 64 KiB) and verify with `cuFileDriverGetProperties().nvfs.max_direct_io_size` (KB). CFG advises keeping defaults ("We recommended that you use the default values for max_direct_io_size_kb, max_device_cache_size_kb, and max_device_pinned_mem_size_kb unless a storage provider has a specific recommendation, or analysis and testing show better performance"), so treat this as "verify, then A/B".
* **[DOC]** Large requests and BAR: DES §6.3 (section 2.3): when a transfer exceeds BAR1 it is chunked through an intermediate buffer.

### 3.3 Optimal request size and the concurrency needed to saturate NVMe

**[MEASURED]** NVIDIA CFG §5.1 (NVIDIA DGX-2, ext4 on a RAID0 of two NVMe SSDs "each SSD is configured with around 3.4GB/sec large read performance", GPU and SSDs under the same PCIe switch, gdsio `-x 0`, 120 s):

|---|---|---|---|---|---|
| 1 MiB read (`-i 1M`, GPU 2, affine) | 8 | 6.52 GiB/s | 1,197 us | ~6.7k | ~3.4 GB/s per drive, ~27k IOPS/drive (iostat), `rxpci` ~8.9 GB/s |
| 1 MiB read, GPU 12 (not under the NVMe's switch) | 8 | 3.89 GiB/s | 2,003 us | ~4.0k | "a 40% decrease in throughput and a 2X increase in latency" |
| 4 KiB random read (`-I 2`, GPU 0, affine) | 4 | 0.093 GiB/s | 163 us | 24,468 | NVIDIA's table |
| | 8 | 0.188 | 162 us | 49,255 | |
| | 16 | 0.385 | 159 us | 100,928 | |
| | 32 | 0.909 | 139 us | 238,245 | |
| | 64 | 1.849 | 135 us | 484,612 | |
| | 128 | 3.243 | 152 us | 850,240 | ~425k IOPS per drive, within a ~800k IOPS/drive spec |
| 4 KiB random read, GPU 10 (not affine) | 64 | 0.106 | 2,301 us | ~28k | "IOPS dropped from 850k IOPS to about 28k IOPS" |

**[DOC]** the same section: "for small, random IO loads, a large number of threads generating load are necessary to assess peak performance capability. Second, for small, random IO loads, the performance penalty of a sub-optimal configuration is much more severe than was observed with large throughput-oriented IO loads." And CFG §8.2: "For IO loads that tend to be small (< 500kB), the performance metric of relevance is IO operations per second (IOPS) and latency, versus throughput ... If assessing maximum throughput is the goal, larger IO sizes should be used when benchmarking."

**[DOC]** Concurrency is the application's job: OVR §1.2.2.2: "Concurrent transfers for each 4 x 4 NVMe PCIe device is necessary to get full bandwidth from one x16 PCIe link. Since there are PCIe links to each GPU and to each NIC, many concurrent transfers are necessary to saturate the system. GDS does not boost concurrency, so this level of performance tuning is managed by the application." DES §6.1: "It takes at least 4 x4 PCIe drives to saturate a x16 PCIe link."

**[MEASURED]** NVIDIA cuDF blog B3 (section 1.6): best end-to-end read throughput at **8-32 threads and 1-16 MiB slices**.

**[MEASURED]** NVIDIA P2PDMA test (P2P, single local NVMe, 4 threads, 1 MiB, `-s 1g`, ext4 `data=ordered`): GPUD read 3.229 GiB/s (1,209 us), CPUONLY 3.228 GiB/s (1,209 us), CPU_GPU 3.191 GiB/s (1,223 us). I.e. when one drive is the bottleneck, GDS equals the CPU path; GDS's benefits then are CPU/memory-bandwidth savings, not throughput. NVIDIA staff on a similar user question (forum, `kmodukuri`, 2023-06-20): "The GPUD, CPUONLY and CPU_GPU look good as the disk bandwidth is the bottleneck (PCIe Gen 3 x4) and not the mode of transfer here. with GPUD you would see slight decrease in the CPU usage at these IO sizes." and "GPUD still consumes CPU as the App is host code and the control path still uses CPU."

**[INFERENCE]** Closed-loop sizing rule (Little's law). With `T` threads/streams each issuing back-to-back reads of size `S` with average completion latency `L`, throughput = `T*S/L`. NVIDIA's numbers satisfy it (8 x 1 MiB / 1.197 ms = 6.5 GiB/s; 128 x 4 KiB / 151.5 us = 3.3 GiB/s). So the **in-flight request count needed** is `BW_target * L / S`:
* Gen5 NVMe ~12-14 GB/s, 1 MiB reads, L ~0.5-1 ms: ~6-14 in flight.
* Same drive, 4 MiB reads, L ~1-2 ms: ~3-7 in flight.
* 4 KiB random reads at ~1M IOPS with L ~135 us: ~135 in flight (NVIDIA needed 128 threads for 850k IOPS).
The in-flight count is limited by *your* concurrency source: number of threads (sync API), number of streams AND `execution.max_io_threads` (stream API; default 4 per GPU), number of batch handles in flight (batch API). Start the reactor with >= 16 in-flight reads of 1-8 MiB per NVMe group and measure; one outstanding stream per GPU would be queue depth 1.

### 3.4 Why small IO is worse with GDS than the CPU path, and where NVIDIA draws lines

* **[DOC] Documented small-IO penalties:**
  * BP Table 4.1: threadpool: "Higher CPU cost for smaller IO sizes (4k-64k)"; stream API: "Higher execution latency for IO size (<1 MB)"; unregistered: API §3.2 "Not using cuFileBufRegister might not be performant for small IO sizes."
  * **REL §10 known issue (kernel dependent):** "Due to a change in pin_user_pages_fast, upstream kernels 6.11 and later, as well as corresponding recent RHEL kernels, exhibit a performance regression for small I/O sizes up to 128 KB. This regression affects both the NVMe nvidia-fs path and the p2pdma path." (This host runs kernel 7.0; so does any production host on a recent kernel.)
  * Fixed per-IO kernel work: TRB §7.6 shows `nvfs_mgroup_pin_shadow_pages` costing 16-32 us per call (pinning shadow pages with `get_user_pages_fast`), plus DMA mapping for the GPU pages.
  * OVR §1.2.3: among the cases "handled seamlessly" by falling back: "The requested IO size is too small, and the filesystem cannot support RDMA." (RDMA filesystems only.)
  * For distributed filesystems NVIDIA ships explicit small-IO cutoffs: `fs:lustre:posix_gds_min_kb` ("IO threshold for read/write (4K aligned) that is equal to or below the threshold that cuFile will use for a POSIX read/write. It was observed that for smaller IO size such as 4KB/8KB, setting this threshold to 4KB/8KB yields better performance."); CFG: "When using Lustre, for small IO sizes, the POSIX path can have better (lower) latency." BeeGFS has the same key. TRB §6.11: "if the posix_gds_min_kb config property is set to a certain value (in KB), the IO for which the size is less than or equal to the set value, will fall back to POSIX mode."
  * Poll mode: `properties:use_poll_mode` (false) / `poll_mode_max_size_kb` (4): "a read or write issued that is less than or equal to properties:poll_mode_max_size_kb (4KB by default) will result in the library polling for IO completion, rather than blocking (sleep). For small I/O size workloads, enabling poll mode may reduce latency." The shipped JSON adds: "Note : currently the overall IO will still be synchronous". Caveat (TRB §10.9, EXAScaler): with poll mode on, `cuFileRead` "might return bytes that are less than the bytes that were requested ... check for returned bytes and continues until all of the data is consumed."
  * Driver stats overhead: NVFS: "Read and write counters are disabled by default because they can affect small-I/O performance." (`/sys/module/nvidia_fs/parameters/rw_stats_enabled`); TRB cheat sheet: "Make sure nvidia-fs read/write stats are disabled."
* **[DOC]** **No NVIDIA document defines a GDS-vs-POSIX size threshold for local NVMe (ext4/XFS).** The 1 MiB figure that appears in BP is about the *stream API's* execution latency, not a general cutoff; "64K and above" appears for the threadpool, "< 64KB" for batch.
* **[DOC]** Counter-statement to keep in mind: OVR §1.2.1: "The latency improvements from GDS are most apparent with small transfers." (Conflicts with BP/REL and most measurements below; it describes the ideal zero-copy path, not the measured small-IO path.)
* **[MEASURED]** Conflicting data, all conditional on who the bottleneck is (details in section 6): vendor/third-party runs show GDS *ahead* at 4 KiB when the CPU/bounce path is saturated (Micron/SNIA: +121% throughput at 4 KiB, -56% latency, "Negligible at large IOs"; KIOXIA: advantage at 4 KiB, "almost identical" beyond), and *behind or equal* in single-thread/latency-bound runs (forum: 4 KiB sync 72 us vs CPU-only 59 us; Gen5 md0, 1 MiB, 1 thread: 1.9 vs 5.7 GiB/s, unresolved).
* **[INFERENCE]** A defensible routing policy for the reactor, to be replaced by measured values on the production machine: POSIX (`pread` into pinned staging + `cudaMemcpyAsync`) for logical reads below a threshold `T_small`; GDS above. `T_small` should be **kernel-aware** (>= 128 KiB on kernels >= 6.11 per REL), **API-aware** (>= 1 MiB if you insist on the stream API per BP), and **tunable at runtime**, with the default derived from a one-time microbenchmark on the target host rather than a constant. Re-test with `n_posix_reads` / `n_p2p_reads` to ensure the "GDS" side is really GDS.

### 4.2 Filesystems, mount options, open flags

* **[DOC]** Classification (REL §7): "EXT4, XFS, DDN EXAScaler, IBM Spectrum Scale, WekaFS, BeeGFS, NFS, ScaTeFS, VirtioFS" are "Enterprise/Deployment"; "TMPFS, OverlayFS, ZFS, BTRFS" are "Developer Friendly" (compat mode). "Filesystems such as TMPFS do not support O_DIRECT mode." REL 1.17: "Updated the compatibility path to support ZFS and BTRFS across all I/O APIs." REL §11: "GDS Compatibility mode is only tested on GDS qualified file systems: ext4, EXAScaler, Amazon FSx for Lustre, XFS, WekaFS, IBM Spectrum Scale, VAST, and BeeGFS."
* **[DOC] ext4 needs `data=ordered`, spelled out in the mount options.** TRB §16.7/§17.6: "Currently, EXT4 and XFS are the only block device based file systems that GDS supports. Because of Direct IO semantics, the EXT4 file system must be mounted with the journaling mode set to data=ordered. This has to be explicitly part of the mount options so that the library can recognize it: `sudo mount -o data=ordered /dev/nvme0n1 /mnt`. If the EXT4 journaling mode is not in the expected mode, the cuFileHandleRegister will fail, and an appropriate error message will be logged in the log file." With compat mode allowed the failure is silent (section 5.1). Check with `findmnt -no OPTIONS <mount>` / `mount | grep ext4` (NVIDIA's check, TRB §16.8). No special XFS mount option is documented.
* **[DOC]** Block-device constraints: "NVMe devices must be compatible with GDS; the device cannot have the block device integrity capability." (`cat /sys/block/<nvme>/integrity/device_is_integrity_capable`, TRB §17.4); P2P mode needs namespaces formatted "with Protection Information - Metadata Size set to zero bytes" (symptom `Tid: 0 incomplete Write, done = 0 issued = 1048576`, TRB §5.16; fix `nvme format -l <LBAF with 0 metadata>`); "The library has a limitation when identifying the NVMe-based block devices in that it expects device names to have the nvme prefix" (TRB §16.12); RAID: "Currently, GDS only supports RAID 0" (TRB §17.5; REL 1.19 adds RAID1/10), "RHEL 8.3 or later does not have default udev rules for detecting RAID members, which disables GDS on RAID volumes" (REL §11), RAID groups should be built from drives with PCI affinity to the GPU: "If affinity is not enforced, GDS will use an internal mechanism of device bounce buffers to copy data from the NVMe devices to an intermediate device that is closest to the drives and copy the data back to the actual GPU." (TRB §17.9).
* **[DOC]** File-open flags accepted by `cuFileHandleRegister` (API §5.2.1): `CU_FILE_INVALID_FILE_OPEN_FLAG` "if the file is opened with unsupported modes such as no O_APPEND, O_NOCTTY, O_NONBLOCK, O_DIRECTORY, O_NOFOLLOW, O_NOATIME, and O_TMPFILE."; `CU_FILE_INVALID_FILE_TYPE` "if the file path is not valid, not a regular file, not a symbolic link, or not a device file." TRB §4.3 lists the same without `O_NOATIME` (`O_APPEND | O_NOCTTY | O_NONBLOCK | O_DIRECTORY | O_NOFOLLOW | O_TMPFILE`) and adds that `FS_COMPR_FL | FS_ENCRYPT_FL | FS_APPEND_FL | FS_IMMUTABLE_FL` files "are allowed when compat_mode is set to true". **[INFERENCE]** The reactor must not pass an fd opened with `O_NOATIME` or `O_NONBLOCK` to cuFile (open a dedicated fd for cuFile; keep any other flags on the POSIX fd).
* **[DOC]** Since 1.7, fds opened without `O_DIRECT` are accepted: API §5.2.1: "CUDA toolkit 12.2 (GDS version 1.7.x) supports non O_DIRECT open flags as well as O_DIRECT. ... In the latter case [nvidia-fs installed], an O_DIRECT path between GPU and Storage will be used if such a path exists." OVR §1.2.1: "even for files opened in non-O_DIRECT mode, the cuFile library takes the GDS driven O_DIRECT path for transfers between GPU memory and storage for page aligned buffers with aligned sizes and offsets." ODI: "Outside of compatibility mode, the APIs will fail if O_DIRECT is not possible." BP §4.2 note: "In compatibility mode, an additional file descriptor can be opened on the file without requiring O_DIRECT mode. This mode can also handle unaligned reads/writes, even when POSIX cannot." The header's `cuFileHandleRegister` comment ("CU_FILE_INVALID_FILE_OPEN_FLAG if file is opened with unsupported modes like no O_DIRECT") is stale relative to 1.7+.
* **[DOC]** DFS: NFS/Lustre/Weka/GPFS/BeeGFS need RDMA-capable storage clients and `libcufile_rdma.so`; ODI §3.2: "File system implementations that do not support RDMA on the server side will not support GDS." REL §11: "Checksums on the client-side of file systems must be disabled for GDS." Batch not available for Spectrum Scale/Weka/BeeGFS (API §8); stream APIs for GPFS/Weka are compat-only (REL §11).

### 4.3 Page cache

* **[DOC]** TRB §8.1: "When using GDS, files are often opened with the O_DIRECT mode. When IO is complete, in the context of DIRECT IO, it bypasses the page cache. Starting with CUDA toolkit 12.2 (GDS version 1.7.x) files can also be opened with non-O_DIRECT mode. Even in such a case, whenever the library software deems fit, it will follow the GDS enabled O_DIRECT path. This conserves coherency by default." EXAScaler: "For reads, IO bypasses the page cache and fetches the data directly from backend storage. When writes are issued, the nvidia-fs drivers will try to flush the data in the page cache for the range of offset-length before issuing writes" (stats `pg_cache`, `pg_cache_fail`, `pg_cache_eio`). nvidia-fs stats: read `io_state_err` "Some pages might have been in the page cache."
* **[DOC]** ODI §3.1 (non-O_DIRECT fd, compat path): "For all other cases the APIs go via the page cache for fds opened in non O_DIRECT mode. This can be viewed as the compatibility mode leveraging the page cache that can typically be used for smaller file I/Os with a high degree of temporal locality, like the case of application headers or metadata."
* **[DOC]** TRB §6.13: "applications should avoid mixing O_DIRECT and normal I/O to the same file and to overlapping byte regions in the same file. Even when the file system correctly handles the coherency issues in this situation, overall I/O throughput might be slower than using either mode alone. Similarly, applications should avoid mixing mmap(2) of files with direct I/O to the same files." (Same sentence in LNX `open(2)`.)
* **[DOC]** CFG §8.2: "Any performance evaluation of the storage technology requires bypassing the page cache to ensure that actual storage performance is being measured, and not the page cache read/write performance." B3: "For accurate I/O benchmarking ... file system caches must be cleared before each new read operation."
* **[INFERENCE]** (a) A GDS/O_DIRECT read never benefits from page-cache-resident data; if the working set is hot in the page cache the buffered CPU path wins (section 6: `CPU_CACHED_GPU`). (b) If the disk tier is written with *buffered* writes and later read with O_DIRECT, the kernel must write back dirty pages first (Linux DIO semantics; LNX warns about mixing). Write the spill files with O_DIRECT (aligned) as well, and fdatasync once per file, so reads do not pay hidden writeback and the benchmark baselines (`dd iflag=direct`, `gdsio`) are comparable. (c) The unaligned-write POSIX fallback writes into the page cache (CFG), another reason to keep writes aligned.

### 4.4 PCIe topology, ACS, IOMMU, P2P modes, NUMA

* **[DOC] Topology is the first-order effect.** BP §3.1: "For the P2P DMA to function efficiently, NICs, NVMes and GPUs should be under a PCIe switch when possible." "Avoid configurations where the NICs are assigned across the CPU sockets that require PCIe traffic to cross the CPU root ports or go across CPU sockets that use QPI." CFG §4: "which IO devices and GPUs are on the same PCIe switch or root complex; which device communication paths require traversing multiple PCIe ports and possibly crossing CPU socket boundaries". NVIDIA staff (forum, `kmodukuri`, 2022-11-21): "The performance of GDS in P2P mode depends upon the PCie distance between the GPU and NVMe drives. Best performance is seen when the NVMe and GPU are under a common PCIe switch. so if the NVMe's are connected over the CPU root port, the performance of p2p might not be optimal. ... If the two NVMe's are across two different CPU sockets, then P2P might not be efficient." Measurements in section 3.3 (-40% bandwidth, 850k to 28k IOPS). **[DOC]** CFG §5.1: when the GPU is not affine, "The cuFile library will select a GPU for the data buffers (GPU memory) that is on the same PCIe switch as the storage ... The data is then moved to the target GPU" (extra copy via a bounce on another GPU).
* **[DOC] ACS.** BP §3.1: "ACS forces P2P PCIe transactions to go up through the PCIe Root Complex, which does not enable GDS to bypass the CPU on paths between a network adapter or NVMe and the GPU in systems that include a PCIe switch. For optimal GDS performance, disable ACS." TRB §3.1: kernel parameter `pci=disable_acs_redir=pci:0:0`; verify with `journalctl -k -b | grep -i 'acs'` ("Configured ACS to 0x0000"); `gdscheck -p` lists "Found ACS enabled for switch ...".
* **[DOC] IOMMU.** BP §3.1: "When the IOMMU setting is enabled, PCIe traffic will be routed through the CPU root ports. This routing limits the maximum achievable throughput ..." TRB §3.1: "In our experience, iommu=off provides the best functionality and performance. On certain platforms, such as DGX A100 and DGX-2, iommu=pt is supported. iommu=on is not guaranteed to work functionally or performantly." REL §11: "On x86-64 platforms, GDS with 'IOMMU=on' or ACS enabled are not guaranteed to work functionally or in a performant way." NVIDIA staff on GH-57 (2025-05-07, `KiranModukuri`): "We support with IOMMU=off or pt if traffic has to go through root port."
* **[DOC] Three data-path modes** (OVR §1.3.2, API §4.1.1 `CUfileP2PFlags`, `gdscheck` "DRIVER CONFIGURATION"): `nvfs` (nvidia-fs.ko + patched NVMe driver from MLNX_OFED/DOCA), `p2pdma` (upstream Linux PCI P2PDMA; no nvidia-fs), `dmabuf` (1.17+), `c2c` (Grace). OVR: "As of CUDA 12.8, GDS supports additional peer-to-peer DMA for NVMe devices using upstream kernel PCI P2PDMA infrastructure for x86_64 platforms (local or remote with SNAP). This feature will no longer depend on nvidia-fs.ko or custom patches to nvme.ko." TRB §16.5: "NVMe P2PDMA mode takes precedence if NVMe is supported by both PCI P2PDMA and nvidia-fs." `cuFileDriverSetP2PFlags` (1.16): on x86_64 only `CU_FILE_P2P_FLAG_PCI_P2PDMA`, on AARCH64 only `CU_FILE_P2P_FLAG_C2C`.
* **[DOC] P2PDMA requirements** (P2P doc, TRB §16): kernel >= 6.2 on Ubuntu (RHEL >= 5.14 / 9.4) with `p2pdma_pgmap_ops` in `/proc/kallsyms`; "OpenRM version 565.47 or above"; "A100, A40, L4, L40S, H100, H200, B100, B200, B300 are supported" (TRB §16.2); `options nvme_core multipath=N`; `options nvidia NVreg_RegistryDwords="RMForceStaticBar1=1;RmForceDisableIomapWC=1;"` (pre-Hopper add `ForceP2P=0;`); `"use_pci_p2pdma": true` plus `"block": {"nvme": {"use_pci_p2pdma": true}}`; "Make sure ACS is disabled and IOMMU is pt or off."; RAID0 and multipath unsupported on x86 ("GPUDirect Storage with NVME P2PDMA feature is not supported with RAID0 and multipath NVMe support."). Known issues (REL §10): "NVME P2PDMA can fail on x86_64 platforms when KASLR is enabled in the linux kernel. The feature can be disabled by specifying the nokaslr kernel parameter."; "Without nvidia-persistenced enabled, NVME P2PDMA can increase the time taken to start the driver initialization for B200 platforms"; "NVME P2PDMA mode is currently not supported on RHEL 9.5 for x86"; "Sparse file IO performance on Ext4 with NVME P2PDMA is slower on x86_64 platforms compared to GDS P2PDMA with nvidia-fs.ko". For nvidia-fs mode: "If you plan to use nvidia-fs to access local NVMe drives, DOCA version compatibility depends on your Linux kernel version: On Linux kernel 6.17 or newer, DOCA 3.3.0 or newer is required ... On Linux 6.17 and later with nvidia-fs mode enabled, the NVMe patch has a known issue with drives that support scatter-gather lists (SGLs) ... use the p2pdma path on these kernels."
* **[DOC] nvidia-fs/NVIDIA driver coupling.** NVFS: "nvidia-fs must be rebuilt or reinstalled after an NVIDIA driver upgrade that changes exported P2P symbols"; "Version 2.17.5 and later requires the NVIDIA UNIX Open Kernel Module on x86_64"; REL §10: P2P interface version `0x00020000` from R580.82.05 requires rebuilding `nvidia-fs.ko` (**[MEASURED]** symptom: GH-66 "Incompatible page table version 0x00020000" followed by a kernel BUG); "Using nvidia-fs version 2.25.6 may cause cuFile APIs to fail when using GDS P2P mode ... We recommend using nvidia-fs version 2.25.7 or newer".
* **[DOC] NUMA.** TRB cheat sheet: "Numa affinity: Set numa affinity of the process where NIC-GPU are in the same switch." B2 states that the CPU threads used to interact with the DMA engine are bound to the closest CPU core. gdsio takes `-n <numa node>`. **[INFERENCE]** Pin the reactor's cuFile worker threads to the NUMA node of the NVMe/GPU pair (use `nvidia-smi topo -m`/`-mp`, `gdscheck.py -t` "print optimal GPU/device pairings (quick view)", `lspci -tv`).
* **[DOC] Multi-GPU.** Per-process caps apply "across all GPUs" (TRB §6.4); `CUFILE_VISIBLE_DEVICES` restricts GPUs; dynamic routing is for DFS (OVR §1.2.6); static topology file and `cuFileExportPCIeTopology(filename)` (1.17, HDR line 786) for deterministic routing; "RAID Group Configuration for GPU Affinity" (section 4.2). **[MEASURED]** (CFG §5.1) with a non-affine GPU the pool/bounce buffers were allocated on another GPU (`PER_GPU POOL BUFFER STATS: GPU : 0 pool_size_MiB : 64 usage : 63/64`).
* **MIG / vGPU / containers.** **[DOC]** The only MIG mention is a debugging checklist row: "MiG mode enabled? Check if MIG is enabled: nvidia-smi mig -lgi" (TRB §22). REL: "GDS now supports vGPU in VMware context" (1.2.1); "vGPU supports the latest GPUs with OpenRM; that is, GPUs with Ada Lovelace, Hopper and later are supported." No statement that GDS works (or not) on MIG slices: open question Q10. Containers: OVR §1.4.2: "Containers include only user-level code and rely on kernel-level components having been installed on the host machine."; API `force_compat_mode`: "the admin can unload the nvidia_fs.ko or not expose the character devices in the docker container environment." (`/dev/nvidia_fs[0-15]`, API §5.1.1 `CU_FILE_PERMISSION_DENIED`).

## 5. Known pitfalls and failure modes

### 5.1 Silent compat-mode fallback: causes and how to detect it

**Why it is silent.** **[DOC]** `allow_compat_mode` defaults to `true`: "If true, falls back to using compatibility mode when the library detects that the buffer file descriptor opened cannot use GPUDirect Storage." (API §3.3). The API's own return values do not say which path served an IO; compat IO is "POSIX pread, pwrite, and aio_submit APIs respectively to host memory and copying to GPU memory when applicable."

**Documented triggers (all [DOC], API §3.3 and TRB):**
* "The nvidia_fs.ko driver is not loaded. All IO operations will use compatibility mode." (or `/dev/nvidia_fs*` not exposed in the container; `force_compat_mode`).
* "No BAR1 memory in GPU." / "Bounce buffers cannot be allocated in GPU memory." / GPU not a supported data-center/Quadro part with compute capability > 6 (REL §5: "All other cards are supported only in compatibility mode.").
* Filesystem/mount not GDS-ready, denylisted mount, unsupported file attributes/open flags (TRB §4.3, §6.12), ext4 without an explicitly visible `data=ordered` (section 4.2), block device with integrity capability, `nvme` naming, RAID without udev rules.
* Config switches: `force_compat_mode`, `gds_rdma_write_support=false` (writes), `fs.generic.posix_unaligned_writes`, `fs.lustre|beegfs.posix_gds_min_kb`, `fs.weka.rdma_write_support=false`, `fs.gpfs.gds_write_support=false`, `rdma_dynamic_routing_order=[SYS_MEM]`. Stream and batch calls on Spectrum Scale/Weka always use compat IO.
* P2PDMA/C2C selected but unsupported (`use_pci_p2pdma` true but kernel/driver registry not set: gdscheck shows `NVMe P2PDMA : Unsupported`).
* Library/driver mismatch cases: REL §10: "With libcufile version 1.16.0, when nvidia-fs is loaded but the NVMe/NVMeoF driver is not patched for GDS support, I/O operations on block devices may incorrectly attempt to use the GDS path and fail. This issue only affects file descriptors registered after the first one on the same block device."
* **[MEASURED]** GH-87 (2026-08, open; closing comment by the reporter says it is a DOCA-OFED 26.01 naming defect already fixed in 26.04): nvidia-fs 2.27-2.29 bound `nvme_v1_register_nvfs_dma_ops` while the DOCA nvme exported `nvme_v2_...`, so "every cuFile read silently falls back to compat mode" while "cuFile reads return correct data, so nothing looks wrong from the application side. The only signal is that `Ops: Read=` in `/proc/driver/nvidia-fs/stats` stays at zero, and cufile.log reports compat mode with a shadow buffer." `/proc/driver/nvidia-fs/modules` did not list `nvme`.
* **[MEASURED]** NVIDIA GDS-team triage of a user report (forum, https://forums.developer.nvidia.com/t/gds-seems-to-consume-more-cpu-and-memory-resources-than-expected/319012, `kmodukuri`): "Also please check if for some reason, the IO is going in compatible mode. check for log entries in cufile.log." The log contained `ERROR cufio-fs:79 mount option not found in mount table data device: /dev/nvme2n1`, `ERROR cufio-fs:152 EXT4 journal options not found in mount table for device,can't verify data=ordered mode journalling`, `NOTICE cufio:293 cuFileHandleRegister GDS not supported or disabled by config, using cuFile posix read/write with compat mode enabled`. Reply: "You are running in compatible mode. please unmount and mount the drive with data=ordered option". After the remount "the CPU utilization is dropped from 246% to 115%". The same three messages (line numbers differ by version, e.g. `cufio-fs:148`, `cufio:1036`) appear in forum thread 234925 and on slide 9 of the GWDG deck (section 6).

**Detection matrix** (use several; none alone is sufficient):

| Signal | How | Source |

### 5.3 Error-code semantics

* **[DOC]** `cuFileRead`/`cuFileWrite` (API §5.2.3): "Size of bytes that were successfully read. -1 on an error, so errno is set to indicate filesystem errors. All other errors return a negative integer value of the CUfileOpError enum value." API §4.1.2 note: "Data path errors are captured via standard error codes by using errno. The APIs will return -1 on error." Helper macros (HDR): `IS_CUFILE_ERR(err)` = `abs(err) > CUFILEOP_BASE_ERR` (5000), `CUFILE_ERRSTR(err)`. All other APIs return `CUfileError_t{err, cu_err}`; "All error code values, other than CU_FILE_SUCCESS, are considered failures that might leave the output and input parameter values of APIs in an undefined state." For `CU_FILE_CUDA_DRIVER_ERROR` the CUDA code is in `cu_err`.
* **[DOC] (NVIDIA-authored code comment, NIXL `gds_mt_engine.cpp`)**: "cuFileRead/cuFileWrite report filesystem errors as -1 with errno set, and cuFile-level errors either as a negative CUfileOpError return value (as documented) or, as observed in practice, as -1 with the CUfileOpError code stored in errno. strerror is only meaningful for the first case." **[INFERENCE]** Decode with: `code = (ret == -1) ? errno : -ret; if (IS_CUFILE_ERR(code)) ... CUFILE_ERRSTR(code) else strerror(code)`.
* Codes you will meet (**[DOC]** API §4.1.3 unless noted): 5001 `CU_FILE_DRIVER_NOT_INITIALIZED` ("The nvidia-fs driver is not loaded."); 5008 `CU_FILE_IO_NOT_SUPPORTED` ("GDS is not supported on the current file."); 5009 `..._DEVICE_NOT_SUPPORTED` (GPU); 5010 nvidia-fs ioctl error; 5011 CUDA driver error (`cu_err`); 5013 `CU_FILE_CUDA_MEMORY_TYPE_INVALID`; 5014 pointer range; 5015 `CU_FILE_CUDA_CONTEXT_MISMATCH`; 5016 `CU_FILE_INVALID_MAPPING_SIZE` ("Access beyond the maximum pinned memory size."); 5017 `..._MAPPING_RANGE` ("Access beyond the mapped size."); 5018 `CU_FILE_INVALID_FILE_TYPE`; 5019 `CU_FILE_INVALID_FILE_OPEN_FLAG`; 5020 `CU_FILE_DIO_NOT_SET` ("The fd direct IO is not set."); 5022 invalid value; 5023 memory already registered; 5024 memory not registered; 5027/5028 handle not/already registered; 5030 `CU_FILE_INTERNAL_ERROR` ("Refer to cufile.log"); 5034 `CU_FILE_IO_DISABLED` ("GDS is disabled by config on the current file."); 5035 batch submit failed; 5036 `CU_FILE_GPU_MEMORY_PINNING_FAILED`; 5037 `CU_FILE_BATCH_FULL`; 5038 `CU_FILE_ASYNC_NOT_SUPPORTED` ("cuFile stream operation is not supported."); 5039-5042 "batch ... internal error - retry later"; 5043 `CU_FILE_NOMEM_ERROR` ("cufile no memory error - retry later"); 5044 `CU_FILE_IO_ERROR`; 5045 buf registration error; 5047 `CU_FILE_INVALID_CONTEXT_ERROR`; 5048 nvfs internal driver error; 5049 `CU_FILE_BATCH_NOCOMPAT_ERROR` ("compat mode off error"). ### 5.4 EOF and short reads

* **[DOC]** The return value is "Size of bytes that were successfully read" (API §5.2.3); for stream: `*bytes_read_p`; for batch: `CUfileIOEvents_t.ret` ("-ve error or amount of I/O done").
* **[DOC] (official sample, behaviour inferred from code)** `2_cuFile_Multithreaded/highly_concurrent_halfreg.cc` computes `nr_ios = fileSize / CHUNK_SIZE` (+1 if there is a remainder), calls `cuFileRead(handle, buf, CHUNK_SIZE, offset, 0)` for every chunk including the last partial one, treats only `ret < 0` as failure and advances `offset += ret`. So a request that crosses EOF returns the partial byte count, like `pread`, rather than an error.
* **[DOC]** NVIDIA's NIXL treats any completion with `ret != requested` as failure ("GDS batch entry completed X of Y bytes"; "GDS_MT: error: short read"), i.e. it clamps/validates sizes up front. DDN EXAScaler: "With 2.12.5_ddn10, any reads beyond EOF causes a BUG_ON inside nvidia-fs." (REL §10). Poll mode on striped Lustre can return short counts mid-file (TRB §10.9: "This behavior is POSIX compliant ... we recommend that the application checks for returned bytes and continues until all of the data is consumed.").
* **[INFERENCE]** Clamp every request to the known file size (cache `st_size`, refresh on writes), and loop on short returns for non-EOF shortfalls. With O_DIRECT, the final partial block read can still deliver only the valid bytes; verify on the target fs (Q13).

### 5.5 Device-context requirements

* **[DOC]** "The APIs with GPU buffers should be called in a valid CUDA context and stream if applicable." (API §3); stream APIs: "The current context of the caller is assumed."; BP §3.2: internal D2D copies are posted "on a stream created on the primary CUDA context"; BP IO Pattern 6: "A cudaContext must be established in each thread before registering the GPU buffers." All samples call `cudaSetDevice(gpuid)` in each worker thread. Errors: `CU_FILE_CUDA_CONTEXT_MISMATCH` (5015), `CU_FILE_INVALID_CONTEXT_ERROR` (5047).
* **[DOC] (NVIDIA staff, forum)** cuFile's internal worker threads retain the primary context: `CUFileThreadPoolWorker::run(): Assertion 0 failed` when `cuDevicePrimaryCtxRetain` fails (`CU_COMPUTEMODE_EXCLUSIVE_PROCESS`). "a given process (across its various threads) is able to use just one CUDA context on a given GPU device at a time. The default CU_COMPUTEMODE_DEFAULT would have been able to allow multiple contexts on the GPU device at the same time".
* **[INFERENCE]** On every reactor thread that calls cuFile: `cudaSetDevice(target)` first; keep application kernels on the primary context (RMM/cuDF default); do not run cuFile hosts in `EXCLUSIVE_PROCESS` compute mode; one process per GPU set. NIXL's MT workers call `cuFileRead` without an explicit `cudaSetDevice` (they only set it at memory-registration time), which suggests cuFile can derive the context from the pointer, but that is not documented (Q15).

### 5.6 `cuFileHandleRegister`: cost, caching, rules

* **[DOC]** API §5.2.1: "cuFileHandleRegister is required and performs extra checking that is memoized to provide increased performance on later cuFile operations." API §3.2: it "evaluates the suitability of the file state and the file mount for GDS and initializes the file state of the critical performance path." BP §4.2: "checks the ability of the named file, at its mount point, to be supported via GDS on this platform ... There should be only one handle created for each file descriptor. The same handle can be shared by multiple threads."
* **[DOC]** Errors: `CU_FILE_HANDLE_ALREADY_REGISTERED` "if the file is already registered using the same file-descriptor"; "A return value of anything other than CU_FILE_SUCCESS leaves fh in an undefined state but has no other side effects." Zero the `CUfileDescr_t` (`memset`) before use (every NVIDIA sample does; kernel-side fields).
* **[DOC]** Teardown: API §5.2.2: "This API should be invoked only after the application ensures there are no outstanding IO operations with the handle. If cuFileHandleDeregister is called while IO on the file is in progress might result in undefined behavior." "The user is still expected to close the file descriptor outside the cuFile subsystem after calling this API using close system call." "Closing a file handle without calling cuFileHandleDeregister does not release the resources that are held in the cuFile library. If this API is not called, the cuFile subsystem releases the resources lazily or when the application exits." So deregister then close, never close then forget.
* **[MEASURED]** Registration does real work: the first handle per block device logs `cufio-fs: Block dev: /dev/nvme1n1 numa node: 0 pci bridge: 0000:3a:02.0`, RAID-member discovery, `mount option` parsing (forum logs); in compat mode driver open performs topology detection with "high startup latency ... on systems with multiple PCI devices" (CFG: `skip_topology_detection`). No NVIDIA number for per-handle cost.
* **[INFERENCE]** Cache `(fd, CUfileHandle_t)` per file in the reactor with a reference count; register once at open, deregister when the last in-flight IO completes and before `close`. Call `cuFileDriverOpen()` explicitly at startup (BP §4.1: "to avoid the latency of the driver initialization that will be otherwise incurred in the first IO call"). No document gives a maximum number of open handles (Q9).

### 5.7 Other documented pitfalls

* **[DOC]** `fork()`: "cuFile APIs are not supported with applications that use the fork() system call." (REL §11; BP, API §3); also LNX: do not fork with O_DIRECT I/O in flight on private mappings.
* **[DOC]** Shutdown: API §5.1.2: "Any in-flight IO when cuFileDriverClose is in-progress will receive an error." HDR: `CU_FILE_DRIVER_CLOSING` "if there are any active IO operations using cuFileRead or cuFileWrite". BP §4.8: call `cuFileDriverClose()` at the end "to reduce the tear-down time ... (i.e. expedited release of pinned GPU buffers and other cuFile resources)". REL §10: with `cufile_stats` non-zero, "the cuFile library may crash during program exit if opened or closed through the dl interface. Workaround: Explicitly call cuFileDriverClose API before closing the library." API §3.2: "Not using the cuFileDeregister and cuFileDriverClose APIs ... might unnecessarily consume resources".
* **[DOC]** Logging and stats cost: TRB §5.3 "Logging will have performance impact as we increase the verbosity levels like INFO, DEBUG, and TRACE, and should be enabled only to debug field issues."; "cufile IO mode: POSIX" is in the hot path; nvidia-fs `rw_stats_enabled` off by default for small-IO performance; cuFile stats level 3 "has the highest performance overhead".
* **[DOC]** Mixed fds: "applications should avoid mixing O_DIRECT and normal I/O to the same file and to overlapping byte regions" (section 4.3).
* **[DOC]** nvidia-fs/NVIDIA kernel interplay on free: "nvidia-fs can deadlock ... when the user frees the CUDA memory without calling cuFileBufDeregister" (section 2.6).
* **[DOC]** Memory-model limits: "cuFile APIs are currently explicit, and reading or writing between storage and buffers that completely fit into the available GPU physical memory. Rather than fine-grained random access, the cuFile APIs are a suitable match for coarse-grained streaming transfers." (OVR §1.1.3).

### 6.3 Conditions where GDS does **not** win (synthesis)

1. **Single drive is the bottleneck**: GDS == CPU path (NVIDIA P2PDMA test; NVIDIA staff statement; forum 256809; KIOXIA "almost identical").
2. **GPU and NVMe not under the same PCIe switch / across sockets / ACS or IOMMU on**: up to -40% throughput, 2x latency, and 30x fewer 4 KiB IOPS (NVIDIA CFG §5.1); cross-root-complex with compat disabled may not even register (GH-70).
3. **Small IO, low concurrency, kernels >= 6.11**: fixed per-IO pinning/mapping cost (16-32 us for shadow-page pinning, TRB §7.6), the documented `pin_user_pages_fast` regression up to 128 KB, and extra stream-API latency (+70 us at 4 KiB).
4. **Page-cache-hot data**: GDS (O_DIRECT) cannot use the cache; the cached CPU path measured 22.4 GiB/s vs 5.2 GiB/s (forum 234925) and 9.3 vs 8.9 GiB/s at 32 threads (forum 277650).
5. **Unaligned or unregistered tiny IO**: bounce-buffer path ("Not using cuFileBufRegister might not be performant for small IO sizes").
6. **Compat mode** (no nvidia-fs/P2PDMA, wrong mount options): "GDS" API is POSIX + copy; numbers say nothing about GDS.
7. **Writes of large sizes with misaligned segments** (IIT: CPU_GPU faster for large writes), and unaligned writes (read-modify-write).
8. **DFS misconfiguration** (RDMA/NIC affinity): NFS/RDMA 3x slower than CPU path in GH-30.
9. **The CPU-bound legacy path is the reason GDS wins in vendor data**: when the bounce path is CPU-limited (many drives/GPUs, many small IOs), GDS wins big (Micron/SNIA 2021, GWDG 4M sequential read on 2 Lustre nodes: 70,726 vs 45,988 MiB/s); on a modern host with a few fast NVMe and many cores, the CPU path is rarely the limiter at >= 1 MiB.

## 8. Recommended design (all [INFERENCE], to be validated by section 10)

1. **Default read path:** synchronous `cuFileRead` on a shared per-file handle from a fixed worker pool (start 16-32 threads per GPU-NVMe group; requests 1-16 MiB, aligned to 4 KiB with the destination aligned to 64 KiB when possible), mirroring what NVIDIA's cuDF/NIXL do. Keep `cuFileReadAsync` only behind a feature flag for stream-ordered use.
2. **If keeping the stream API:** per-slot stream + `cuFileStreamRegister(stream, 0xF)` at startup; pinned `bytes_read` slots; never share a stream across threads (or guard with a mutex); gate on `fflags & (1u<<CU_FILE_STREAMS_SUPPORTED)`; set `execution.parallel_io=true`, `max_io_threads` >= concurrent streams, `max_io_queue_depth` > in-flight cap; deregister before destroy.
3. **Registration policy:** none by default; optional small pool of long-lived registered staging buffers (<= a few hundred MiB per GPU, 64 KiB-aligned, registered at startup with RAII owner that deregisters before free); never register pool-managed or one-shot destinations.
4. **Configuration (explicit, not implicit):** ship an app `cufile.json` (set via `CUFILE_ENV_PATH_JSON` or `cuFileSetParameter*` before `cuFileDriverOpen`): `allow_compat_mode=false` on GDS CI machines; `max_direct_io_size_kb=16384` (verify); slab config sized for peak concurrent unregistered IOs (counts of 1/8/16 MiB slabs >= in-flight reads); `max_device_pinned_mem_size_kb` >= cache + registered; `io_priority` tuned if GPU is compute-busy; `profile.cufile_stats=3` in test runs.
5. **Alignment layer:** align (file offset, size) to 4 KiB, destination pointer and size to 64 KiB (over-allocate from RMM), clamp to file size, trim after read.
6. **Small-read policy:** POSIX path below a runtime-calibrated threshold (>= 128 KiB on kernels >= 6.11; >= 1 MiB with stream API); batch API only if many small reads must be amortized (entries <= bounce size on <= 1.17).
7. **Startup self-check:** `cuFileDriverOpen`, `cuFileDriverGetProperties`, `cuFileDriverGetP2PFlags`, `cuFileGetBARSizeInKB`, mount-option check (`data=ordered`), `statx(STATX_DIOALIGN)`, and a one-IO canary with stats to confirm the mode; log the result.
8. **Hygiene:** `cudaSetDevice` per thread; handle cache with refcounts; deregister handles/buffers/streams before close/free/destroy and before `cuFileDriverClose`; no `fork`; treat `bytes<0` using the `errno`-or-negative decoding.

- Section 4.3.4, IO Pattern 4: "An IO is unaligned if one of the following conditions is true: The `file_offset` that was issued in `cuFileRead` or `cuFileWrite` is not 4K aligned. - Section 3.3: "For the requested IO size, GDS issues IO requests sequentially in chunks of reads/writes based on the `max_direct_io_size` parameter. Larger values ... will result in a reduced number of calls to the IO stack and might result in higher throughput."
